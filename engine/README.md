# gdd, the deterministic layer of GDD

`gdd` is a small command-line tool for projects that use Gate-Driven Development, contract `gdd/1`. The skills keep the judgment: what to brief, the tests, the code, the review and talking to the person. This tool keeps what a model following text gets wrong: the order of the steps, the accounting of limits and the evidence. It reads the files the skills already leave in a project (`gdd/blueprint.md`, `gdd/log/*.jsonl`, `gdd/briefs/`, `gdd/backlog.md`), so a project needs no change of the contract to use it.

What it is not: it doesn't make a gate impossible to skip. While an agent runs it, it is within the agent's reach, like any file of the repository. What the platform can enforce is `gdd verify` and `gdd gates` run in CI as a required check, out of the builder's reach. What it does make sure of is that it offers no easy way around its own checks: see [What it can't stop](#what-it-cant-stop).

## Build

```sh
sh build.sh     # builds outside the repository and prints where the binary is
sh build.sh test     # unit tests and the integration tests under tests/
```

`build.sh` runs `cargo build --release` with its target folder outside the repository and prints where the binary is. Don't build into `engine/target/`: cargo hard-links what it builds, and the eval harness refuses a plugin that holds a file with two names. A plain `cargo build` or `cargo test` from inside the repository builds outside it too, next to the repository's folder, because of `.cargo/config.toml` at its root, and `scripts/check_skills.py` fails while an `engine/target/` exists. The layer runs where there is a POSIX shell and git: macOS and Linux, and Windows under WSL. `GDD_TARGET_DIR` picks the folder, and `GDD_GIT` the git the layer runs when the one on the path can't be trusted (see `src/git.rs`).

Rust 1.89 or later. It needs `git` and `sh` on the path when it runs, and nothing else: no network, no database, no git library. A clean release build took about 7 seconds here and gives a binary of about 3.5 MB.

## The rules it keeps

- **A change's state comes only from its log and git.** One function, `state::derive`, reads the log of a change in order, with what `judged::GitView` asked git: the tip of the change's branch, the seal's tip and the main branch. Every command takes the color, the brief's version, `<base>`, `<start>`, what the color asks for, what passed on the current head, the rounds used, the open question to the person and the one next step from there.
- **Only the tool writes the log, each event through its own command.** One line per call, appended, with the clock's time at that moment, hashes from `git hash-object`, fields checked against the shape of the event. An event the state doesn't allow is refused with why and what to do instead. Every event of the contract has a command that checks what it records, so the layer takes no event an agent composed: `gdd log` writes nothing and names the command to use. A line is never edited: `gdd correct` appends a `correction` that names it.
- **What was judged is what ships.** The gates judge from the tip of `gdd-seal/<id>`, never from a `<start>` the log alone gives. A change ships only when its state, derived on the commit that ships, is ready to ship, and that commit is the one its last passing gates and its review judged, or differs from it only in the layer's own bookkeeping. A local merge merges that commit by its hash.
- **Its outputs stay private.** The gates' outputs, a role's prompt and output and what a merge sets aside go to a folder of the user's own, `gdd-runs-<uid>` in the temporary folder (`GDD_RUNS_DIR` overrides it): created with mode 0700, and used only while it is a real directory, not a link, owned by the user and not writable by anyone else; otherwise the run says why and uses a fresh private folder. Each file in it is created new, so a link planted at its path is never followed and nothing there is truncated.
- **Every command ends with `gdd {json}`**, the same facts for a program, after short plain lines for the agent. Exit codes: 0 fine, 1 refused, a check failed or a cap spent, 2 called wrong or something missing. A refusal says why in `reason` (`out-of-order`, `needs-approval`, `cap-spent`, `cannot`...), and something missing (`"reason":"missing"`) is named both in its printed line and in a `what` fact: the file, the ref, the branch, the step.
- **Nothing is sealed or built where git can't write.** Before `brief` writes its step, before `seal`, `gates` (without `--at`), `ship --bookkeeping` and `ship --merge`, and before `launch <id> checks|build`, the layer creates and deletes a throwaway ref, `refs/gdd-probe/<random>`. If git can't, it refuses with code `cannot` and the words "git can't write a ref here: nothing can be sealed or built", and `next` gives the same as the reason a change is stopped when its next step would write git (brief, checks, build, gates, ship).
- **Every invocation is journaled** in `gdd/log/<id>.engine.jsonl` (`blueprint.engine.jsonl` for the project's): the command, its arguments without free text, its exit code, its milliseconds, when it refused, why, and the log line it wrote, if any (`wrote`), so `verify` can tell the layer's lines from lines written by hand. `--no-journal` or `GDD_NO_JOURNAL=1` turns it off, for reading someone else's project. There is no single journal for the whole project on purpose: every change's bookkeeping commit would carry a different tail of it, and two changes shipped by pull request would conflict on it. `gdd metrics --all --format jsonl` gives every call from every journal, without knowing the ids and without git.

After a command writes a log event, its last human-readable lines give the same next step and command as `gdd next <id>`. The JSON keeps the command just run in `command`, the next step in `next` and what runs it in `next_command` (empty when done). A failed gates run still exits 1 and gives the remedy. A refusal that wrote nothing keeps its own explanation. Read `next` at the start, after compaction, when unsure or after a step outside the layer such as a merge. A write and its next step count as one invocation. A blueprint write with no open question omits the handoff. Use `gdd next` for project status.

## Commands

Run them from a project's root, or point at one with `--root <project>`. `--branch` names a change's branch when it isn't `work/<id>`, `gdd-build/<id>` or `build/<id>`; `--head` names the commit to judge instead of the branch's tip. It only names it: the state is derived on that commit, so it never makes ready to ship a change that isn't, and a `--head` that names no commit is refused (`"reason":"missing"`), never taken as the branch. A `--head` or `--branch` that starts with `-` is refused (`"reason":"usage"`), and every revision reaches git after `--end-of-options`, so none is ever taken for one of git's options.

## Evidence in role reports

In the builder's `gdd-report` block, repeat `decision:` for each product choice the brief or request left open. Use `decision: none` if there are none. The build step records the first 12 choices in `decisions`, up to 240 Unicode characters each after removing control characters, line separators and invisible direction and spacing marks. This leaves room for a dozen short product rules and caps the builder's contribution at 2,880 characters before quoting. Numbered items, bullets, bold labels, `decisions:` and `none.` are also accepted. A missing list or a merge confined to corrected tests keeps the last known product choices. The review prompt asks the reviewer to check those choices against the written rules and cite any conflict. Once the change is in, both `ship --merge` and `ship --done` print each choice for the orchestrator to pass on.

For each check the blueprint selects for the color and planned paths with `cases: each change`, yellow needs a `rejects` proof. It records `passes` if a correct version already exists. Red needs both for the same check. Extra passing runs are kept. Setting up a standing check needs both proofs once its `when` is empty or matches a tracked file. A prose-only revision reuses sealed proofs that still apply. The layer checks them against the revised paths and includes any new runs in the report. A green change without a brief runs the existing checks. A stopped checks role reports its blocker. If evidence is missing, the step stays open. The role supplies the missing runs and submits the same seal with `gdd report <id> checks <file>`, optionally with `--proofs <json file>`.

A scenario test's rejecting proof includes `test` (its name) and `wrong` (the wrong solution its assertions reject). The run is recorded separately in the same entry by its command, exit and tail. A review that asks for a `fix` gives each numbered finding a citation after ` | ` on its own line. Use `@id:<scenario>`, `zone <name>: <rule>`, `constitution: <rule>`, `request: <the person's words>` or `check <id>` from the blueprint. On red, each finding then ends with ` | ran: <command>`, a command of the reviewer's json block; the last `| ran:`, in any case, starts it, and quotes, backticks, a trailing stop or `(exit N)` don't count. A fix without numbered findings, with an uncited one or, on red, one without its run is refused (`unbacked-fix`), naming each finding once and what it lacks, and the closest command of the json block when the run named another; a fix whose color rose is written anyway. The reviewer who wrote it sends its whole report again, resumed with `launch --run --command` or by hand: until a line is written, other refusals included, `launch --run` alone is refused and the prompt repeats what each finding lacked, kept in the journal's `unbacked`. Where the color asks for `person-review`, the reviewer's prompt asks for evidence for the person in `.gdd/evidence/<id>/` when it passes, listed under `EVIDENCE:`, which a blank line or a numbered finding ends, and a pass keeps it in the step's `evidence`, bounded as the builder's product choices are. A blank line after an item closes `LATER:`. On a later review, put the resolved findings once each in the report field, for example `closed: f1=fixed f2=intended`. The other outcomes are `false` and `minor`. An empty line closes nothing. Spaces and commas separate pairs. With an unknown or repeated id or an invalid outcome, the layer writes the review, closes no findings and reports the text it saved in `unparsed_closed`. The `reviewed:` line from the prompt identifies the commit, branch tip and gate run. If any changes, rerun the review. A manual `pass` needs the commit. If the reviewer omits it, `--run` checks the value it sent at launch. A `fix` or `stop` can omit it. An explicit `--closed` supplies the entire list instead.

In a brief reading, number only the proposed additions. More than three returns `too-many-additions` before the step is recorded. List gaps that make existing scenarios untestable under `MISSING:` without numbers. The report prints the gaps and records them in `missing` for the orchestrator to resolve before approval. To choose destinations for numbered additions, launch the reading without `--run` and use `--went` on the report. Unassigned findings stay in the log. A reading can report `pass` with observations under `LATER:`, which the layer records in `later` for the log alone.

## How a change's state is derived

The log is read line by line. A `brief` step sets the color, the version, the base (kept from the first brief) and `<start>` when it carries a seal; a `seal` event and a `checks` step move `<start>` to the seal's new commit, and what the seal held unrecorded when a `seal` event moved `<start>` past it still counts in the next checks report, so a checks step voided by a correction and then a merge of the main branch loses nothing; a `gates` step carries the `<start>` it judged from and, when this tool wrote it, the `head` it judged. The gates still take `<start>` from git and check the log agrees with it. A new brief or checks step starts the judging over: the gates and the review of the build before it no longer count, and the next step is a new build. The head of the change's branch stands for the commit its gates or its review judged when it differs from it only in the layer's own bookkeeping: `gdd/backlog.md` and the files directly in `gdd/log/` named `<id>.jsonl` or `<id>.engine.jsonl` for a valid id, nothing in a subfolder and nothing with another name, each holding on the branch the blob of the working copy's file, or the blob a bookkeeping commit of the layer put there, between the judged commit and the head, as the change's journal records it. Anything else a builder puts under `gdd/log/` is judged like any other file. And a review still holds after a merge of the main branch, or of the seal, that touched none of the files the change touched as reviewed, so that merge asks for the gates again and not for a review. On red, the brief is read (`gdd launch <id> reading`) before the person is asked to approve it. An approval holds while the brief calls for the same scenario files with the same hashes. A waiver, a new version number or an edit to the list of paths does not reopen that approval. A question is open while nothing follows its `ask`. The limits are counted as `gdd/limits.sh` counts them, so a cap that has no room left stops the next round but never the gates, the review or the ship of a build already finished. From all this and git's tip of the change's branch, one next step comes out: brief, reading, ask, wait, checks, build, gates, review, ship, close or done, or stopped with a code (`cap-spent`, `review-stop`, `seal-broken`, `cannot`, `needs-person`). When it is ship, it names both ways a project may ship, the local merge first when the repository has no remote.

Where a change stands once it shipped is derived too, and nothing is written when it starts to wait or closes by itself. One whose last `brief` step has the three lines in `closing` waits for a `close` event with a `yes` or a `no`, however long: its step is `in-use`, and a `not-yet` leaves it there. One with no `closing`, or with `nothing` in it, is `done` from its `ship` and closed once the blueprint's `closing.days` go by after it, unless before that someone said `not-yet`, a question of `close` is open, or a `harden` step in the blueprint's log names it in `change` after its `ship`: then it waits for a verdict too. A wait for a person after the `ship` is no work on the change: its minutes stop there. `closing.who` names who gives the verdict, the change's author when it names nobody. A blueprint without `closing` was written before version 0.16 and reads as before: a change that promised nothing is closed when it ships. A setup log promises nothing to anyone and has nothing to close.

A setup log (`standing-checks`, `standing-checks-<check>`, `gates-<zone>`) has no brief: its checks step starts from where `gdd-seal/<id>` was cut from the main branch, takes its color from the paths it sealed (written in the step as `color`, `"on":"sealed"`), and its trial judges all it sealed. Its branch is its seal: `ship --bookkeeping`, `--merge` and `--done` ship `gdd-seal/<id>`. The person reviews it with `ask --of change` and `approve --of change` where its color asks for `person-review`. When its trial says `stop`, the person is told (`gdd ask <id> --of stop`), and then comes a fix round, `gdd launch <id> checks`, whose prompt carries the trial's findings and the person's answer, and a new trial: a stop is never waived, only a trial that passes lifts it. In a fix round, what the checks role sealed is what the seal holds that the trial didn't judge: a fix sealed before the main branch was merged into the seal, or one that came through the main branch with the person's approval, counts, and gets its new trial. A setup log has no gates of its own. For `standing-checks` in a project with no code yet, the prompts say that only the seal and the secret scan are set up now, and every other check waits with its `when`.

## Stopped, and the way on

No state of a log answers the same refusal whatever the orchestrator does: each one `next` stops in names what moves it.

| Stopped (`blocked`) | When | The way on |
|---|---|---|
| `needs-person` | A question to the person is open, or the color asks for their approval | What `gdd ask` printed for that kind: `gdd approve`, `gdd waiver` or `gdd answer` |
| `needs-person` after two refusals | The journal shows the same refusal twice for the suggested step at the same seal and head. A usage error, a missing resume command or a brief waiting for the standing checks leaves the count unchanged | `gdd ask <id> --of decision "<one proposed fix in the person's words>"`, then record their answer and act on it. For `vague-stop`, identify the blocked scenario or missing file before another attempt. |
| `cap-spent` | A cap has no room for a new round | If the person delegated and the next item can proceed, defer the change with `gdd brief <id> --stop` without asking. Otherwise ask once with `--of waiver`. Say what is done, what is missing, what was spent and what one extra attempt would buy. Propose the extra attempt if other work needs this one. Record agreement with `gdd waiver`. Otherwise propose deferring. Record an explicit choice to wait with `gdd answer` and close a deferred change with `gdd brief <id> --stop "<their words>"`. For deferred setup, `next` names the question to reopen when the person wants to resume. |
| `standing-checks` | A brief needs the project’s standing checks | `gdd next standing-checks` gives the next setup step. The brief can start when that backlog item is done. |
| `cannot`, the brief stopped | The change was dropped | A new brief takes it up again: `gdd brief <id> ...` |
| `cannot`, the checks stopped twice | gdd-checks couldn't write a check | The person decides (`gdd ask <id> --of decision`); then a new version of the brief, or, if they said so, `gdd launch <id> checks --level deep` |
| `cannot`, a setup's checks stopped twice | gdd-checks couldn't set a check up, or fix it after its trial | The person decides (`gdd ask <id> --of decision`); with their answer, `gdd launch <id> checks` once more, and a new stop goes to them again. If they leave it for later, it stays in the backlog: only `standing-checks` comes before a request |
| `cannot`, the builder stopped | The builder said `CANNOT:` | A new version of the brief, or new checks if one looks wrong |
| `cannot`, git can't write | No ref can be written here | Work where git can write, then `gdd next <id>` |
| `cannot`, git has no author | git has no name and email to write a commit with, as on a machine nobody set up | The person says whose name and email this copy's commits carry; set them in the repository (`git config user.name`, `git config user.email`), then `gdd next <id>` |
| `seal-broken` | The gates found what judges the change touched | Tell the person (`gdd ask <id> --of stop`); then a fix round that puts it back as sealed, `gdd launch <id> build`, and the gates |
| `review-stop` | The reviewer, or a setup log's trial, said stop | Tell the person (`gdd ask <id> --of stop`); then a fix round (`gdd launch <id> build`, or `checks` for a setup log) and a new review or trial. A stop is never waived |

When a review raises the color, the command for the new brief includes the paths that set its floor. If a new review is needed after a bookkeeping commit, its prompt and its report use the product commit the gates judged.

A launch prompt or a status read between two refused reports leaves both attempts in view. The journal records the refs as the command judged them, including after a role run by the layer. A different refusal, a recorded answer or step, or a changed seal or head breaks the sequence. A journal from an older layer has no refs for its refusals, so they cannot count toward the pair.

Every refusal of a command names what to run instead, or what to do; one that leaves nothing else names `gdd next <id>`, and a change that shipped says that anything more is a new change with an id of its own, and names `gdd close <id>` while it waits for a verdict.

What sent a change back holds whatever command comes next, and not only in what `next` names. When every finding of a `fix` names a check sealed for the change, `next` returns the findings to the checks agent. If the checks agent answers `CANNOT`, all the findings go to the builder for a counted fix. Otherwise the builder merges the new seal and reports the build. Git compares the merge with the commit that passed the gates before the review. Edits confined to tests the checks agent had already sealed use no build round. At the build-round limit the builder can only merge the seal. A product edit needs the person's agreement to another attempt or the change waits. Its time and tokens count. The gates run again. A fresh reviewer gets the previous findings and retests only what changed, down to the named tests when the product is unchanged. With mixed findings the checks agent corrects its named tests first and the builder handles the remaining findings. When none names a sealed test, the whole review goes to the builder. After a `stop`, the builder fixes the change. In a setup log the checks agent fixes the checks before their next trial. After a `stop`, or gates that found what judges the change touched, that round waits for the person to be told and to answer. Commits on the branch that nobody logged change none of it. Gates that failed may run again on the same commit, but not on another one before a build step reports the round that moved the branch: `next` names that report. A branch that only took the main branch in, through its seal, has no round to report. The line that sent the change back is never voided, and neither is any line of a change that shipped, except a `close` written wrong. The layer checks the caps that apply to the round at the log's last line. A build that finishes after its time runs out is still written and judged. `gdd verify` gives an error for a void of a line that sent the change back, and a warning for one of any other gates or review step.

One refusal comes before every command, `verify` included: a repository git won't read, as it won't one another user owns, which is what a checkout in a CI container often is. Taken for a folder with no git, the logs would be checked alone and pass. The layer says what git said and names the line that marks the folder as safe (`git config --global --add safe.directory <folder>`), for whoever decides that copy is the one to trust. Only `gdd verify --no-git`, which asks for no git, goes on without it.

## What stays with the agents

Everything that takes judgment: what the change is for and its scenarios, the color judgment raises, the tests, the code, the review and its findings, the words to the person and their decisions. The tool never writes a brief, a test or code, never decides a color lower than git's floor, never approves and never pushes; it merges only when asked to with `gdd ship <id> --merge`, for a project whose constitution ships that way. Before the gates, in their fresh copy, it runs the blueprint's `install` when there is one, and writes what it took in the step. Without one, a check that ends with exit 127, command not found, is the copy lacking what the check needs: the layer refuses with `environment`, writes nothing, counts no round, and names `--at` with a checkout where the dependencies are installed, such as CI's. An `install` that fails is refused the same way.

A program that uses the library calls `commands::finish` after it journals a call (`journal::record`), as the binary does: that is where `ship --merge` commits the ship's bookkeeping, journal line included.

## Events it may write beyond the contract's template

- `answer`: the person's words, the kind of question and the line of the `ask` it answers.
- `correction`: the line it corrects, what was wrong and, with `void`, that the line decides nothing more for the change.
- `seal`: the seal moved, with its ref, the commit it was at (or was cut from), the new one, why, and for files the hashes it sealed:
  `{"contract":"gdd/1","ts":"<UTC time>","brief":"<id>","event":"seal","ref":"gdd-seal/<id>","from":"<commit, or null>","to":"<commit>","why":"<sealed <files>, or merged <main branch>>","files":{"<path>":"<git blob hash>"}}`
- Extra fields: `head` in `gates` and `ship` (the commit judged and shipped), `skipped` in `gates`, `fix_role`, `notes` and `later` in `review`, `seal_only` in a build bringing in corrected checks, `request` in `brief` (the person's words), and in a `ship` matched by content, `"matched":"content"` and `in`, the commit of the main branch that holds what was judged (`gdd verify` checks it the same way).

Older logs can omit these fields. A counter copied before decision 85 charges a build for merging corrected tests until the project updates its copy. What a voided line used counts in both. What it decided, such as the room a waiver gave, counts only in the script, which reads no correction.

The journal, beyond the call: a `ship` that committed bookkeeping keeps `"bookkeeping":{"commit":"<commit>","parent":"<commit>","files":{"<path>":"<git blob hash>"}}`, the files that commit changed. That is how the layer knows later that a head carries its own bookkeeping and nothing else. With the journal turned off, only the working copy's own content counts.

## What it can't stop

The layer refuses what is out of order and offers no shortcut of its own: no event written by hand through it, no `--head` that makes a change ready, no `<start>` taken from the log alone, no file under `gdd/log/` riding along unjudged, no merge of a branch that moved, no ship recorded from ancestry alone, no squash that brought more than the judged files. But it runs within reach of the agent that runs it, and an agent that goes around the layer instead of through it can still:

- run `gdd approve` itself, in the person's name, without asking them. The log can't tell who typed the command. Only a person approving on a platform, by a path no agent has, such as a review of a pull request on a protected branch, closes that.
- write the log or the journal by hand, or move `gdd-seal/<id>` with git and write the log to match. `gdd verify` catches some of it (steps out of order, sealed hashes that aren't git's, a gates `<start>` that isn't the seal's, steps written in the same second), and the gates refuse a seal that moved where the log doesn't say. A seal moved and logged by hand to agree with it passes, and so does an unlogged commit on the seal that `gdd seal` then seals on top of. A protected `gdd-seal/<id>` branch on the platform closes that.
- name with `--head` a tip that ends the change before its last commits, when the change went in by a fast-forward with no branch left and something that isn't bookkeeping follows it: that tip is the person's word, and the layer checks only that nothing but bookkeeping comes between the judged commit and it.
- get past `--done` with a rebase merge that added a commit touching none of the change's files before or after the rebased ones, or with a merge commit whose own resolution added content: the first looks like another change's commit, and the layer doesn't redo the merge to compare. A squash, and what a merge's other parent brought, are checked whole.

The platform's required check, `gdd gates` and `gdd verify` run in CI on what the pull request merges, closes both.
- run the checks' commands, or anything else, outside the layer.

What closes these is the platform, out of every agent's reach: required checks in CI, protected branches and approvals only a person can give.
