# gdd, the deterministic layer of GDD

`gdd` is a small command-line tool for projects that use Gate-Driven Development, contract `gdd/1`. The skills keep the judgment: what to brief, the tests, the code, the review and talking to the person. This tool keeps what a model following text gets wrong: the order of the steps, the accounting of limits and the evidence. It reads the files the skills already leave in a project (`gdd/blueprint.md`, `gdd/log/*.jsonl`, `gdd/briefs/`, `gdd/backlog.md`), so a project needs no change of the contract to use it.

What it is not: it doesn't make a gate impossible to skip. While an agent runs it, it is within the agent's reach, like any file of the repository. What the platform can enforce is `gdd verify` and `gdd gates` run in CI as a required check, out of the builder's reach. What it does make sure of is that it offers no easy way around its own checks: see [What it can't stop](#what-it-cant-stop).

## Build

```sh
sh build.sh     # builds outside the repository and prints where the binary is
sh build.sh test     # unit tests and the integration tests under tests/
```

`build.sh` runs `cargo build --release` with its target folder outside the repository and prints where the binary is. Don't build into `engine/target/`: cargo hard-links what it builds, and the eval harness refuses a plugin that holds a file with two names. A plain `cargo build` or `cargo test` from inside the repository builds outside it too, next to the repository's folder, because of `.cargo/config.toml` at its root, and `scripts/check_skills.py` fails while an `engine/target/` exists. The layer runs where there is a POSIX shell and git: macOS and Linux, and Windows under WSL. `GDD_TARGET_DIR` picks the folder, and `GDD_GIT` the git the layer runs when the one on the path can't be trusted (see `src/git.rs`).

Rust 1.89 or later. It needs `git` and `sh` on the path when it runs, and nothing else: no network, no database, no git library. A clean release build took about 7 seconds here and gives a binary of about 3.5 MB.

## The rules it keeps

- **A change's state comes only from its log and git.** One function, `state::derive`, reads the log of a change in order, with what `judged::GitView` asked git: the tip of the change's branch, the seal's tip and the main branch. Every command takes the color, the brief's version, `<base>`, `<start>`, what the color asks for, what passed on the current head, the rounds used, the open question to the person and the one next step from there.
- **Only the tool writes the log, each event through its own command.** One line per call, appended, with the clock's time at that moment, hashes from `git hash-object`, fields checked against the shape of the event. An event the state doesn't allow is refused with why and what to do instead. Every event of the contract has a command that checks what it records, so the layer takes no event an agent composed: `gdd log` writes nothing and names the command to use. A line is never edited: `gdd correct` appends a `correction` that names it.
- **What was judged is what ships.** The gates judge from the tip of `gdd-seal/<id>`, never from a `<start>` the log alone gives. A change ships only when its state, derived on the commit that ships, is ready to ship, and that commit is the one its last passing gates and its review judged, or differs from it only in the layer's own bookkeeping. A local merge merges that commit by its hash.
- **Its outputs stay private.** The gates' outputs, a role's prompt and output and what a merge sets aside go to a folder of the user's own, `gdd-runs-<uid>` in the temporary folder (`GDD_RUNS_DIR` overrides it): created with mode 0700, and used only while it is a real directory, not a link, owned by the user and not writable by anyone else; otherwise the run says why and uses a fresh private folder. Each file in it is created new, so a link planted at its path is never followed and nothing there is truncated.
- **Every command ends with `gdd {json}`**, the same facts for a program, after short plain lines for the agent. Exit codes: 0 fine, 1 refused, a check failed or a cap spent, 2 called wrong or something missing. A refusal says why in `reason` (`out-of-order`, `needs-approval`, `cap-spent`, `cannot`...), and something missing (`"reason":"missing"`) is named both in its printed line and in a `what` fact: the file, the ref, the branch, the step.
- **Nothing is sealed or built where git can't write.** Before `brief` writes its step, before `seal`, `gates` (without `--at`), `ship --bookkeeping` and `ship --merge`, and before `launch <id> checks|build`, the layer creates and deletes a throwaway ref, `refs/gdd-probe/<random>`. If git can't, it refuses with code `cannot` and the words "git can't write a ref here: nothing can be sealed or built", and `next` gives the same as the reason a change is stopped when its next step would write git (brief, checks, build, gates, ship).
- **Every invocation is journaled** in `gdd/log/<id>.engine.jsonl` (`blueprint.engine.jsonl` for the project's): the command, its arguments without free text, its exit code, its milliseconds, when it refused, why, and the log line it wrote, if any (`wrote`), so `verify` can tell the layer's lines from lines written by hand. `--no-journal` or `GDD_NO_JOURNAL=1` turns it off, for reading someone else's project. There is no single journal for the whole project on purpose: every change's bookkeeping commit would carry a different tail of it, and two changes shipped by pull request would conflict on it. `gdd metrics --all --format jsonl` gives every call from every journal, without knowing the ids and without git.

## Commands

Run them from a project's root, or point at one with `--root <project>`. `--branch` names a change's branch when it isn't `work/<id>`, `gdd-build/<id>` or `build/<id>`; `--head` names the commit to judge instead of the branch's tip. It only names it: the state is derived on that commit, so it never makes ready to ship a change that isn't, and a `--head` that names no commit is refused (`"reason":"missing"`), never taken as the branch. A `--head` or `--branch` that starts with `-` is refused (`"reason":"usage"`), and every revision reaches git after `--end-of-options`, so none is ever taken for one of git's options.

|---|---|---|

Without an id: the blueprint's approval, the standing checks, every open question with its wait, the next backlog item, and each line of the backlog it can't read. Only `standing-checks` comes before every change; `standing-checks-<check>` and `gates-<zone>` are items like the rest, in the backlog's order. Changes nothing. | `gdd next empty-cart` |
| `brief <id> [<file>...] --paths <p>... [--color <c> --why "<w>"] [--request "<their words>" or --request-file <file>]` | The `brief` step: the planned color from the paths, the base, the brief's files with their hashes, which must be the seal's. `--request` keeps the person's words, which a change with no brief gives its builder and its reviewer word for word. | `gdd brief fix-footer --paths src/texts/footer.txt --request "the footer says Copyrigth"` |

A question `--of brief` or `--of change` before the change's log has a `brief` step is refused (`out-of-order`); a setup log has no brief, so it takes `--of change` only. Questions `--of decision`, `stop` or `waiver`, and any on the blueprint's log, go any time. | `gdd ask empty-cart --of brief "Approve what it has to do?"` |
| `answer <id> "<their words>"` | Ends the open question with an `answer` event. | `gdd answer empty-cart "yes, two decimals"` |
| `approve <id> --of <kind> --version N --who <p> --where <w> <file>...` | The person's approval, with each file's blob hash as they saw it; refuses a file that isn't the sealed version. `--of change` takes each file as the change's judged head holds it, which the orchestrator's copy may not have at all. | `gdd approve empty-cart --of brief --who Person --where conversation features/empty-cart.feature` |
| `waiver <id> --who --check --why --backlog [--limit <cap> --to N]` | A waived check or limit, and its backlog item. | `gdd waiver empty-cart --who Person --check rounds_per_change --why "one more try" --backlog empty-cart-rounds --limit rounds_per_change --to 4` |
| `correct <id> --line N [--void] "<what>"` | A `correction` of a line; `--void` takes the line out of the change's state: it decides nothing more, and what it used still counts against the caps. Refused for a line that sent the change back, and in a closed log. | `gdd correct empty-cart --line 7 --void "approval written twice"` |
| `report <id> <step> <file or ->` | Writes a launched role's step from its `gdd-report` block, its round counted by the tool. The checks role's proofs come from the `json` block before its report block (`--proofs <file>` overrides it), and so do what a builder says each check gave (`claims`; `--claims <file>` overrides it) and the commands a reviewer ran (`ran`): their prompts ask for that block, and without it the log says so and keeps the list empty. A missing block, a review without a verdict, a build that left nothing or has no branch, and checks before the approval their color asks for are refused. | `gdd report empty-cart review last-message.txt` |
| `limits <id>` | What the limits still allow, counted exactly as `gdd/limits.sh` counts, and one more line, `lines N of C`, with the builder's lines from `<start>` to the change's head, without the bookkeeping, when there is a head. That one goes in the last line as `lines` and never in `stop`. | `gdd limits empty-cart` |
| `verify [<id>... \| --all] [--no-git]` | Integrity for CI: errors exit 1, warnings don't. | `gdd verify --all` |
| `color [<id>] [--paths <p>...]` | The planned color of some paths, or the color of what a change touched from `<start>` to its head. | `gdd color --paths src/cart.py docs/new.md` |
| `zones` | Each zone's pathspec that matches no tracked file, and every tracked file no zone covers. | `gdd zones` |
| `gates <id> [--at <dir>]` | Runs the checks the color asks for on exactly the head of the change's branch, in a throwaway worktree, or in a directory checked to be at that commit with a clean tree, and writes the `gates` step. Every check's command gets what the contract names and the layer knows: `<start>` and `<base>`, full commit hashes git resolved, and `<sealed paths>`, each quoted for `sh`; a hash needs no quotes, so it stands as it is inside the command's own double quotes too, as in `"<start>^{commit}"`. A command that still holds another `<...>`, such as `<head>` or a template's prose, is refused before anything runs (`unfilled`). Its `<start>` comes from git: the tip of `gdd-seal/<id>`, or where there is no local one, as in CI, the one its remotes hold (`origin/gdd-seal/<id>`), which must be the `<start>` the log gives, or the gates refuse (`seal-moved`); a log that knows a seal while git has none is refused too (`seal-missing`): in CI, fetch the seal's branch first (a full fetch brings it). With nothing sealed, `<start>` is where the head meets the main branch (the base, or a later commit of it merged in), and a log that says otherwise is refused (`start-mismatch`). | `gdd gates empty-cart` |
| `launch <id> <role> [--run]` | The exact command and prompt of a role (checks, build, review, reading) from the blueprint's `levels`. The prompt names its skill both ways ("Load the `gdd-checks` skill (`gdd:gdd-checks` when it comes from a plugin)"), gives a reviewer the log's absolute path, and says what a setup log sets up. With `--run`, starts it with standard input closed (a `launch` ending in `< /dev/null` is read without it), checks it wrote something within `--start-wait` seconds (60), stops it past its timeout (the minutes the change has left), reads its last message and its tokens and writes its step. | `gdd launch empty-cart review --run --command "<program> --model <model> <prompt>"` |
| `ship <id> --describe` | The merge request's description, from the log and the brief. | `gdd ship empty-cart --describe` |
| `ship <id> --bookkeeping` | Commits the copy's bookkeeping on top of the change's branch: the backlog, the change's own log and journal, the blueprint's, and those of every change that is over, shipped or dropped. A change still under way ships its log with itself. It does so through a throwaway index, without touching the checkout or its index, and prints the commit. The branch must still be at the head that stands judged (`branch-moved`). The commit goes to the call's journal with the blob of each file it changed: a head that differs from what was judged only in that bookkeeping still counts as judged (see [How a change's state is derived](#how-a-changes-state-is-derived)). | `gdd ship empty-cart --bookkeeping` |
| `ship <id> --merge` | For a project that ships by a local merge: on the main branch, with nothing else pending, it commits the bookkeeping if it wasn't, sets aside the copy's files the branch holds as they are, merges with `--no-ff` the commit that stands judged, by its hash and never the branch by its name (a branch that moved since is refused, `branch-moved`; a conflict only in the bookkeeping takes the copy's version), puts back what the merge didn't bring, checks the head is in the main branch and writes the `ship` step. Once the call is journaled, it commits on the main branch what it doesn't hold yet of `gdd/log/**` and `gdd/backlog.md`, in one commit that touches nothing else ("Log the ship of <id>"), so the checkout is left clean; if it can't, it says in one line that this is bookkeeping, not something to report to the person. | `gdd ship empty-cart --merge` |
| `ship <id> --done <where>` | The `ship` step, only once git shows that what went into the main branch is what was judged; sets its backlog item to `done`. For a project that ships by pull request, after `--bookkeeping`; its `ship` line stays in the copy and travels with the next change's bookkeeping, which it says is not something to report to the person. While the change's branch exists, its tip must be the judged commit or differ from it only in the layer's bookkeeping, `--head` or not (`unjudged`). Then it finds what went in, never from ancestry alone. By a merge: the oldest commit of the main branch's own line that holds the judged commit is the merge that brought it, and its other parent must stand for the judged one, as must a later merge that carries on from the change's own line (`unjudged`). By a fast-forward: after the judged commit only the layer's bookkeeping, up to the branch's tip or the `--head` given; when something else follows and nothing bounds the change, it refuses (`which-tip`) and asks for `--head <the tip that was merged>`, checked the same way. By squash or rebase, where the judged commit isn't in the main branch: the commits of its own line since it met `<start>` that touch the change's files, and any between them, must change nothing but those files and the bookkeeping (`unjudged`), and the last of them must hold the judged blob of every file the change touched (`not-merged`); commits before or after them that touch none of its files are taken for other changes. It says it was matched by content and records where it landed. | `gdd ship empty-cart --done main` |
| `step blueprint <prepare\|harden\|exam> ...` | The orchestrator's own steps in the blueprint's log, in the contract's shapes: `prepare --result <proposed\|approved> [--file <path>]... [--probe '<json>'] [--levels '<json>']`, `harden --crack "<w>" --proposal "<w>" [--change <id>] [--scenario "<file and Rule>"]`, `exam --level <l> --model <m> --asked N --caught N [--missed <id>]...`. | `gdd step blueprint prepare --result proposed --file gdd/blueprint.md` |
| `backlog list \| add \| done \| briefed` | The backlog, one line rewritten at a time. It reads the contract's table and what an agent may write instead: tables under headings of any level (a heading `Phase N` gives the phase of the items under it), several tables, columns renamed (`ID`, `Status`, `Estado`...) or added, ids in backticks or bold, or a list (`- [ ] \`id\`: what (color, phase N, state)`). A line it can't read is named with what it expected, never skipped, and `backlog list` exits 1 (`unreadable`). | `gdd backlog add pages --what "The catalog in pages" --color yellow` |
| `waiting` | Every open question across all logs, oldest first, with how long it has waited. | `gdd waiting` |
| `metrics [<id>... \| --all] [--format json\|jsonl\|csv] [--out <dir>] [--summary]` | Tables of metrics, recomputable from the logs, the journals, the blueprint and git. See [METRICS.md](METRICS.md). | `gdd metrics --all --format csv --out metrics --summary` |

## How a change's state is derived

The log is read line by line. A `brief` step sets the color, the version, the base (kept from the first brief) and `<start>` when it carries a seal; a `seal` event and a `checks` step move `<start>` to the seal's new commit, and what the seal held unrecorded when a `seal` event moved `<start>` past it still counts in the next checks report, so a checks step voided by a correction and then a merge of the main branch loses nothing; a `gates` step carries the `<start>` it judged from and, when this tool wrote it, the `head` it judged. The gates still take `<start>` from git and check the log agrees with it. A new brief or checks step starts the judging over: the gates and the review of the build before it no longer count, and the next step is a new build. The head of the change's branch stands for the commit its gates or its review judged when it differs from it only in the layer's own bookkeeping: `gdd/backlog.md` and the files directly in `gdd/log/` named `<id>.jsonl` or `<id>.engine.jsonl` for a valid id, nothing in a subfolder and nothing with another name, each holding on the branch the blob of the working copy's file, or the blob a bookkeeping commit of the layer put there, between the judged commit and the head, as the change's journal records it. Anything else a builder puts under `gdd/log/` is judged like any other file. And a review still holds after a merge of the main branch, or of the seal, that touched none of the files the change touched as reviewed, so that merge asks for the gates again and not for a review. On red, the brief is read (`gdd launch <id> reading`) before the person is asked to approve it. An approval of the brief counts while every scenario file it names still has the hash of the latest brief step. A question is open while nothing follows its `ask`. The limits are counted as `gdd/limits.sh` counts them, so a cap that has no room left stops the next round but never the gates, the review or the ship of a build already finished. From all this and git's tip of the change's branch, one next step comes out: brief, reading, ask, wait, checks, build, gates, review, ship or done, or stopped with a code (`cap-spent`, `review-stop`, `seal-broken`, `cannot`, `needs-person`). When it is ship, it names both ways a project may ship, the local merge first when the repository has no remote.

A setup log (`standing-checks`, `standing-checks-<check>`, `gates-<zone>`) has no brief: its checks step starts from where `gdd-seal/<id>` was cut from the main branch, takes its color from the paths it sealed (written in the step as `color`, `"on":"sealed"`), and its trial judges all it sealed. Its branch is its seal: `ship --bookkeeping`, `--merge` and `--done` ship `gdd-seal/<id>`. The person reviews it with `ask --of change` and `approve --of change` where its color asks for `person-review`. When its trial says `stop`, the person is told (`gdd ask <id> --of stop`), and then comes a fix round, `gdd launch <id> checks`, whose prompt carries the trial's findings and the person's answer, and a new trial: a stop is never waived, only a trial that passes lifts it. In a fix round, what the checks role sealed is what the seal holds that the trial didn't judge: a fix sealed before the main branch was merged into the seal, or one that came through the main branch with the person's approval, counts, and gets its new trial. A setup log has no gates of its own. For `standing-checks` in a project with no code yet, the prompts say that only the seal and the secret scan are set up now, and every other check waits with its `when`.

## Stopped, and the way on

No state of a log answers the same refusal whatever the orchestrator does: each one `next` stops in names what moves it.

| Stopped (`blocked`) | When | The way on |
|---|---|---|
| `needs-person` | A question to the person is open, or the color asks for their approval | What `gdd ask` printed for that kind: `gdd approve`, `gdd waiver` or `gdd answer` |
| `cap-spent` | A cap has no room for a new round | The person may give more room: `gdd ask <id> --of waiver "<cap>: <used> of <cap> used. One more round would <what it buys>. Yes?"`, then `gdd waiver <id> ... --limit <key> --to <n>`. On a change, split it or leave it in the backlog (`gdd brief <id> --stop "<their words>"`); on `standing-checks`, which every change waits for, the person is asked at once |
| `cannot`, the brief stopped | The change was dropped | A new brief takes it up again: `gdd brief <id> ...` |
| `cannot`, the checks stopped twice | gdd-checks couldn't write a check | The person decides (`gdd ask <id> --of decision`); then a new version of the brief, or, if they said so, `gdd launch <id> checks --level deep` |
| `cannot`, a setup's checks stopped twice | gdd-checks couldn't set a check up, or fix it after its trial | The person decides (`gdd ask <id> --of decision`); with their answer, `gdd launch <id> checks` once more, and a new stop goes to them again. If they leave it for later, it stays in the backlog: only `standing-checks` comes before a request |
| `cannot`, the builder stopped | The builder said `CANNOT:` | A new version of the brief, or new checks if one looks wrong |
| `cannot`, git can't write | No ref can be written here | Work where git can write, then `gdd next <id>` |
| `cannot`, git has no author | git has no name and email to write a commit with, as on a machine nobody set up | The person says whose name and email this copy's commits carry; set them in the repository (`git config user.name`, `git config user.email`), then `gdd next <id>` |
| `seal-broken` | The gates found what judges the change touched | Tell the person (`gdd ask <id> --of stop`); then a fix round that puts it back as sealed, `gdd launch <id> build`, and the gates |
| `review-stop` | The reviewer, or a setup log's trial, said stop | Tell the person (`gdd ask <id> --of stop`); then a fix round (`gdd launch <id> build`, or `checks` for a setup log) and a new review or trial. A stop is never waived |

Every refusal of a command names what to run instead, or what to do; one that leaves nothing else names `gdd next <id>`, and a closed log says that anything more is a new change with an id of its own.

What sent a change back holds whatever command comes next, and not only in what `next` names. After a review that said `fix` or `stop`, no other review and no gates are written until a build step, or new checks in a setup log, answers it. After a `stop`, or gates that found what judges the change touched, that round waits for the person to be told and to answer. Commits on the branch that nobody logged change none of it. Gates that failed may run again on the same commit, but not on another one before a build step reports the round that moved the branch: `next` names that report. A branch that only took the main branch in, through its seal, has no round to report. The line that sent the change back is never voided, and neither is any line of a log that is closed. And a round that began with a cap already spent isn't written, whether `gdd launch` started it or not: what counts is how the caps stood at the log's last line, so a build that ended after its time ran out is still written and judged. `gdd verify` gives an error for a void of a line that sent the change back, and a warning for one of any other gates or review step.

One refusal comes before every command, `verify` included: a repository git won't read, as it won't one another user owns, which is what a checkout in a CI container often is. Taken for a folder with no git, the logs would be checked alone and pass. The layer says what git said and names the line that marks the folder as safe (`git config --global --add safe.directory <folder>`), for whoever decides that copy is the one to trust. Only `gdd verify --no-git`, which asks for no git, goes on without it.

## What stays with the agents

Everything that takes judgment: what the change is for and its scenarios, the color judgment raises, the tests, the code, the review and its findings, the words to the person and their decisions. The tool never writes a brief, a test or code, never decides a color lower than git's floor, never approves and never pushes; it merges only when asked to with `gdd ship <id> --merge`, for a project whose constitution ships that way. Before the gates, in their fresh worktree, it runs the blueprint's `install` when there is one, and writes what it took in the step. Without one, a check that ends with exit 127, command not found, is the copy lacking what the check needs: the layer refuses with `environment`, writes nothing, counts no round, and names `--at` with a checkout where the dependencies are installed, such as CI's. An `install` that fails is refused the same way.

A program that uses the library calls `commands::finish` after it journals a call (`journal::record`), as the binary does: that is where `ship --merge` commits the ship's bookkeeping, journal line included.

## Events it may write beyond the contract's template

- `answer`: the person's words, the kind of question and the line of the `ask` it answers.
- `correction`: the line it corrects, what was wrong and, with `void`, that the line decides nothing more for the change.
- `seal`: the seal moved, with its ref, the commit it was at (or was cut from), the new one, why, and for files the hashes it sealed:
  `{"contract":"gdd/1","ts":"<UTC time>","brief":"<id>","event":"seal","ref":"gdd-seal/<id>","from":"<commit, or null>","to":"<commit>","why":"<sealed <files>, or merged <main branch>>","files":{"<path>":"<git blob hash>"}}`
- Extra fields: `head` in `gates` and `ship` (the commit judged and shipped), `skipped` in `gates`, `notes` and `later` in `review`, `request` in `brief` (the person's words), and in a `ship` matched by content, `"matched":"content"` and `in`, the commit of the main branch that holds what was judged (`gdd verify` checks it the same way).

Readers that don't know them can skip them: `gdd/limits.sh` counts the same with or without them. What a voided line used counts in both. What it decided, such as the room a waiver gave, counts only in the script, which reads no correction.

The journal, beyond the call: a `ship` that committed bookkeeping keeps `"bookkeeping":{"commit":"<commit>","parent":"<commit>","files":{"<path>":"<git blob hash>"}}`, the files that commit changed. That is how the layer knows later that a head carries its own bookkeeping and nothing else. With the journal turned off, only the working copy's own content counts.

## What it can't stop

The layer refuses what is out of order and offers no shortcut of its own: no event written by hand through it, no `--head` that makes a change ready, no `<start>` taken from the log alone, no file under `gdd/log/` riding along unjudged, no merge of a branch that moved, no ship recorded from ancestry alone, no squash that brought more than the judged files. But it runs within reach of the agent that runs it, and an agent that goes around the layer instead of through it can still:

- run `gdd approve` itself, in the person's name, without asking them. The log can't tell who typed the command. Only a person approving on a platform, by a path no agent has, such as a review of a pull request on a protected branch, closes that.
- write the log or the journal by hand, or move `gdd-seal/<id>` with git and write the log to match. `gdd verify` catches some of it (steps out of order, sealed hashes that aren't git's, a gates `<start>` that isn't the seal's, steps written in the same second), and the gates refuse a seal that moved where the log doesn't say. A seal moved and logged by hand to agree with it passes, and so does an unlogged commit on the seal that `gdd seal` then seals on top of. A protected `gdd-seal/<id>` branch on the platform closes that.
- name with `--head` a tip that ends the change before its last commits, when the change went in by a fast-forward with no branch left and something that isn't bookkeeping follows it: that tip is the person's word, and the layer checks only that nothing but bookkeeping comes between the judged commit and it.
- get past `--done` with a rebase merge that added a commit touching none of the change's files before or after the rebased ones, or with a merge commit whose own resolution added content: the first looks like another change's commit, and the layer doesn't redo the merge to compare. A squash, and what a merge's other parent brought, are checked whole.

The platform's required check, `gdd gates` and `gdd verify` run in CI on what the pull request merges, closes both.
- run the checks' commands, or anything else, outside the layer.

What closes these is the platform, out of every agent's reach: required checks in CI, protected branches and approvals only a person can give.
