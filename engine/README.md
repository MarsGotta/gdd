# gdd, the deterministic layer of GDD

`gdd` is a small command-line tool for projects that use Gate-Driven Development, contract `gdd/1`. The skills keep the judgment: what to brief, the tests, the code, the review and talking to the person. This tool keeps what a model following text gets wrong: the order of the steps, the accounting of limits and the evidence. It reads the files the skills already leave in a project (`gdd/blueprint.md`, `gdd/log/*.jsonl`, `gdd/briefs/`, `gdd/backlog.md`), so a project needs no change of the contract to use it.

What it is not: it doesn't make a gate impossible to skip. While an agent runs it, it is within the agent's reach, like any file of the repository. What the platform can enforce is `gdd verify` and `gdd gates` run in CI as a required check, out of the builder's reach.

## Build

```sh
sh build.sh     # builds outside the repository and prints where the binary is
sh build.sh test     # unit tests and the integration tests under tests/
```

`build.sh` runs `cargo build --release` with its target folder outside the repository and prints where the binary is. Don't build into `engine/target/`: cargo hard-links what it builds, and the eval harness refuses a plugin that holds a file with two names. `GDD_TARGET_DIR` picks the folder, and `GDD_GIT` the git the layer runs when the one on the path can't be trusted (see `src/git.rs`).

Rust 1.89 or later. It needs `git` and `sh` on the path when it runs, and nothing else: no network, no database, no git library. A clean release build took about 7 seconds here and gives a binary of about 3.5 MB.

## The rules it keeps

- **A change's state comes only from its log and git.** One function, `state::derive`, reads the log of a change in order and asks git for the tip of the change's branch, the seal's tip and the main branch. Every command takes the color, the brief's version, `<base>`, `<start>`, what the color asks for, what passed on the current head, the rounds used, the open question to the person and the one next step from there.
- **Only the tool writes the log.** One line per call, appended, with the clock's time at that moment, hashes from `git hash-object`, fields checked against the shape of the event. An event the state doesn't allow is refused with why and what to do instead. A line is never edited: `gdd correct` appends a `correction` that names it.
- **Every command ends with `gdd {json}`**, the same facts for a program, after short plain lines for the agent. Exit codes: 0 fine, 1 refused, a check failed or a cap spent, 2 called wrong or something missing. A refusal says why in `reason` (`out-of-order`, `needs-approval`, `cap-spent`, `cannot`...), and something missing (`"reason":"missing"`) is named both in its printed line and in a `what` fact: the file, the ref, the branch, the step.
- **Nothing is sealed or built where git can't write.** Before `brief` writes its step, before `seal`, `gates` (without `--at`), `ship --bookkeeping` and `ship --merge`, and before `launch <id> checks|build`, the layer creates and deletes a throwaway ref, `refs/gdd-probe/<random>`. If git can't, it refuses with code `cannot` and the words "git can't write a ref here: nothing can be sealed or built", and `next` gives the same as the reason a change is stopped when its next step would write git (brief, checks, build, gates, ship).
- **Every invocation is journaled** in `gdd/log/<id>.engine.jsonl` (`blueprint.engine.jsonl` for the project's): the command, its arguments without free text, its exit code, its milliseconds, when it refused, why, and the log line it wrote, if any (`wrote`), so `verify` can tell the layer's lines from lines written by hand. `--no-journal` or `GDD_NO_JOURNAL=1` turns it off, for reading someone else's project. There is no single journal for the whole project on purpose: every change's bookkeeping commit would carry a different tail of it, and two changes shipped by pull request would conflict on it. `gdd metrics --all --format jsonl` gives every call from every journal, without knowing the ids and without git.

## Commands

Run them from a project's root, or point at one with `--root <project>`. `--branch` names a change's branch when it isn't `work/<id>`, `gdd-build/<id>` or `build/<id>`; `--head` names the commit to judge.

| Command | What it does | Example |
|---|---|---|
| `next [<id>]` | The single next step of a change and the command that runs it, or why it is stopped. Without an id: the blueprint's approval, the standing checks, every open question with its wait, the next backlog item. Changes nothing. | `gdd next empty-cart` |
| `brief <id> [<file>...] --paths <p>... [--color <c> --why "<w>"] [--request "<their words>"]` | The `brief` step: the planned color from the paths, the base, the brief's files with their hashes, which must be the seal's. `--request` keeps the person's words, which a change with no brief gives its builder and its reviewer word for word. | `gdd brief fix-footer --paths src/texts/footer.txt --request "the footer says Copyrigth"` |
| `seal <id> <file>...` | Commits files of the working copy on `gdd-seal/<id>`, through a throwaway index: the checkout and its index stay as they were. `--merge-main` merges the main branch into the seal. Either move is written to the log as a `seal` event. | `gdd seal empty-cart gdd/briefs/empty-cart.md features/empty-cart.feature` |
| `log <id> '<event>'` | The validated append of an event an agent composed: the tool sets its time, checks every hash against the working copy, refuses a `gates` or `ship` step. | `gdd log empty-cart '{"event":"step","step":"prepare",...}'` |
| `ask <id> --of <kind> "<what>"` | Starts a wait for the person, at the moment the question goes out, and says what records their answer: `gdd approve` for `blueprint`, `gates`, `debt`, `brief` and `change`, `gdd waiver` for a `waiver`, `gdd answer` for the rest. A question `--of brief` or `--of change` before the change's log has a `brief` step is refused (`out-of-order`); a setup log has no brief, so it takes `--of change` only. Questions `--of decision`, `stop` or `waiver`, and any on the blueprint's log, go any time. | `gdd ask empty-cart --of brief "Approve what it has to do?"` |
| `answer <id> "<their words>"` | Ends the open question with an `answer` event. | `gdd answer empty-cart "yes, two decimals"` |
| `approve <id> --of <kind> --version N --who <p> --where <w> <file>...` | The person's approval, with each file's blob hash as they saw it; refuses a file that isn't the sealed version. | `gdd approve empty-cart --of brief --who Person --where conversation features/empty-cart.feature` |
| `waiver <id> --who --check --why --backlog [--limit <cap> --to N]` | A waived check or limit, and its backlog item. | `gdd waiver empty-cart --who Person --check rounds_per_change --why "one more try" --backlog empty-cart-rounds --limit rounds_per_change --to 4` |
| `correct <id> --line N [--void] "<what>"` | A `correction` of a line; `--void` takes the line out of the change's state. | `gdd correct empty-cart --line 7 --void "approval written twice"` |
| `report <id> <step> <file or ->` | Writes a launched role's step from its `gdd-report` block, its round counted by the tool. The checks role's proofs come from the `json` block before its report block (`--proofs <file>` overrides it). A missing block, a review without a verdict, a build that left nothing or has no branch, and checks before the approval their color asks for are refused. | `gdd report empty-cart review last-message.txt` |
| `limits <id>` | What the limits still allow, counted exactly as `gdd/limits.sh` counts, and one more line, `lines N of C`, with the builder's lines from `<start>` to the change's head, without the bookkeeping, when there is a head. That one goes in the last line as `lines` and never in `stop`. | `gdd limits empty-cart` |
| `verify [<id>... \| --all] [--no-git]` | Integrity for CI: errors exit 1, warnings don't. | `gdd verify --all` |
| `color [<id>] [--paths <p>...]` | The planned color of some paths, or the color of what a change touched from `<start>` to its head. | `gdd color --paths src/cart.py docs/new.md` |
| `zones` | Each zone's pathspec that matches no tracked file, and every tracked file no zone covers. | `gdd zones` |
| `gates <id> [--at <dir>]` | Runs the checks the color asks for on exactly the head of the change's branch, in a throwaway worktree, or in a directory checked to be at that commit with a clean tree, and writes the `gates` step. | `gdd gates empty-cart` |
| `launch <id> <role> [--run]` | The exact command and prompt of a role (checks, build, review, reading) from the blueprint's `levels`. The prompt names its skill both ways ("Load the `gdd-checks` skill (`gdd:gdd-checks` when it comes from a plugin)"), gives a reviewer the log's absolute path, and says what a setup log sets up. With `--run`, starts it with standard input closed (a `launch` ending in `< /dev/null` is read without it), checks it wrote something within `--start-wait` seconds (60), stops it past its timeout (the minutes the change has left), reads its last message and its tokens and writes its step. | `gdd launch empty-cart review --run --command "<program> --model <model> <prompt>"` |
| `ship <id> --describe` | The merge request's description, from the log and the brief. | `gdd ship empty-cart --describe` |
| `ship <id> --bookkeeping` | Commits the copy's logs, journals and backlog on top of the change's branch, through a throwaway index, without touching the checkout or its index, and prints the commit. A head that differs from what was judged only in that bookkeeping still counts as judged. | `gdd ship empty-cart --bookkeeping` |
| `ship <id> --merge` | For a project that ships by a local merge: on the main branch, with nothing else pending, it commits the bookkeeping if it wasn't, sets aside the copy's files the branch holds as they are, merges with `--no-ff` (a conflict only in the bookkeeping takes the copy's version), puts back what the merge didn't bring, checks the head is in the main branch and writes the `ship` step. Once the call is journaled, it commits on the main branch what it doesn't hold yet of `gdd/log/**` and `gdd/backlog.md`, in one commit that touches nothing else ("Log the ship of <id>"), so the checkout is left clean; if it can't, it says in one line that this is bookkeeping, not something to report to the person. | `gdd ship empty-cart --merge` |
| `ship <id> --done <where>` | The `ship` step, only once git shows the change's head in the main branch; sets its backlog item to `done`. For a project that ships by pull request, after `--bookkeeping`; its `ship` line stays in the copy and travels with the next change's bookkeeping, which it says is not something to report to the person. | `gdd ship empty-cart --done main` |
| `step blueprint <prepare\|harden\|exam> ...` | The orchestrator's own steps in the blueprint's log, in the contract's shapes: `prepare --result <proposed\|approved> [--file <path>]... [--probe '<json>'] [--levels '<json>']`, `harden --crack "<w>" --proposal "<w>" [--change <id>] [--scenario "<file and Rule>"]`, `exam --level <l> --model <m> --asked N --caught N [--missed <id>]...`. | `gdd step blueprint prepare --result proposed --file gdd/blueprint.md` |
| `backlog list \| add \| done \| briefed` | The backlog's table, one line rewritten at a time. | `gdd backlog add pages --what "The catalog in pages" --color yellow` |
| `waiting` | Every open question across all logs, oldest first, with how long it has waited. | `gdd waiting` |
| `metrics [<id>... \| --all] [--format json\|jsonl\|csv] [--out <dir>] [--summary]` | Tables of metrics, recomputable from the logs, the journals, the blueprint and git. See [METRICS.md](METRICS.md). | `gdd metrics --all --format csv --out metrics --summary` |

## How a change's state is derived

The log is read line by line. A `brief` step sets the color, the version, the base (kept from the first brief) and `<start>` when it carries a seal; a `seal` event and a `checks` step move `<start>` to the seal's new commit; a `gates` step carries the `<start>` it judged from and, when this tool wrote it, the `head` it judged. A new brief or checks step starts the judging over: the gates and the review of the build before it no longer count, and the next step is a new build. The head of the change's branch stands for the commit its gates or its review judged when it differs from it only in `gdd/log/**` and `gdd/backlog.md`; and a review still holds after a merge of the main branch, or of the seal, that touched none of the files the change touched as reviewed, so that merge asks for the gates again and not for a review. On red, the brief is read (`gdd launch <id> reading`) before the person is asked to approve it. An approval of the brief counts while every scenario file it names still has the hash of the latest brief step. A question is open while nothing follows its `ask`. The limits are counted as `gdd/limits.sh` counts them, so a cap that has no room left stops the next round but never the gates, the review or the ship of a build already finished. From all this and git's tip of the change's branch, one next step comes out: brief, reading, ask, wait, checks, build, gates, review, ship or done, or stopped with a code (`cap-spent`, `review-stop`, `seal-broken`, `cannot`, `needs-person`). When it is ship, it names both ways a project may ship, the local merge first when the repository has no remote.

A setup log (`standing-checks`, `standing-checks-<check>`, `gates-<zone>`) has no brief: its checks step starts from where `gdd-seal/<id>` was cut from the main branch, takes its color from the paths it sealed (written in the step as `color`, `"on":"sealed"`), and its trial judges all it sealed. Its branch is its seal: `ship --bookkeeping`, `--merge` and `--done` ship `gdd-seal/<id>`. The person reviews it with `ask --of change` and `approve --of change` where its color asks for `person-review`.

## What stays with the agents

Everything that takes judgment: what the change is for and its scenarios, the color judgment raises, the tests, the code, the review and its findings, the words to the person and their decisions. The tool never writes a brief, a test or code, never decides a color lower than git's floor, never approves and never pushes; it merges only when asked to with `gdd ship <id> --merge`, for a project whose constitution ships that way. It doesn't install dependencies before the gates: run it with `--at` in a checkout where they are installed, such as CI's.

A program that uses the library calls `commands::finish` after it journals a call (`journal::record`), as the binary does: that is where `ship --merge` commits the ship's bookkeeping, journal line included.

## Events it may write beyond the contract's template

- `answer`: the person's words, the kind of question and the line of the `ask` it answers.
- `correction`: the line it corrects, what was wrong and, with `void`, that the line no longer counts.
- `seal`: the seal moved, with its ref, the commit it was at (or was cut from), the new one, why, and for files the hashes it sealed:
  `{"contract":"gdd/1","ts":"<UTC time>","brief":"<id>","event":"seal","ref":"gdd-seal/<id>","from":"<commit, or null>","to":"<commit>","why":"<sealed <files>, or merged <main branch>>","files":{"<path>":"<git blob hash>"}}`
- Extra fields: `head` in `gates` and `ship` (the commit judged and shipped), `skipped` in `gates`, `notes` and `later` in `review`, `request` in `brief` (the person's words).

Readers that don't know them can skip them: `gdd/limits.sh` counts the same with or without them, except a voided line, which it still counts.
