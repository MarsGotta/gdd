# Setting up the standing checks

The standing checks are the machine checks the blueprint's `checks` name. They hold for the whole project, so they get set up and tried once, never once for each zone, and no change starts before they hold. This is the second part of preparing: the blueprint defined them, and here they get built.

This is yours to start. When the item is still `todo` and someone asks for a change, do this first and then go on with the change, in the same turn: don't ask the person whether to, and never offer to go on without it. Start with `gdd next standing-checks` and follow the command each step prints. They already said yes when they approved the blueprint, so it has no brief and waits for no approval but the one its color asks for when it ships.

1. **The item.** The backlog item is `standing-checks`, its log `gdd/log/standing-checks.jsonl` and its seal `gdd-seal/standing-checks`, cut from the main branch. It has no brief, and its color is the one its paths give: the files of the checks, of CI and of each tool's configuration.
2. **Setting them up.** Launch `gdd-checks` as the layer directs. In a project with no code yet, that is `seal` and `secrets` and CI running them, and nothing else: every other check waits with the `when` the blueprint gives it, and nobody is asked to demonstrate a check on code that does not exist. In a project with code, a check also waits while its `when` matches no tracked file. The role sets each applicable check up, with a tool that already exists before a script of the project's own, proves it once and seals it. With the agent tool, pass its last message to `gdd report standing-checks checks <file>`. A command-line launch with `--run` writes the step itself.
3. **The trial.** Launch a fresh `gdd-review` as the layer directs. It tries each check three ways, once a round: the check rejects a planted bad case, it accepts without it, and a change can't switch it off. When the blueprint names its gates, it also reads each gate's feature against the blueprint, which has to ask for what the feature says. For a manual launch, record its last message with `gdd report standing-checks review <file>`.
   - `fix`: back to `gdd-checks`, and then tried again. Of the blueprint's `limits`, the ones written for every color count here, each launch of `gdd-checks` after the first as a round: this log has no brief, so no color's own caps reach it. Every change waits for these checks. When their rounds run out, say what is missing and propose one more attempt now. Record a yes with `gdd waiver`. If they choose to wait, use `gdd answer` and take up the waiver question when they want to resume.
   - `stop`: tell the person. Either a check can't be made to hold, or its files fall in a zone whose color asks for no `review`, which is a pathspec for them to approve.
4. **What it leaves for later.** Tell the person what the trial left under `LATER:` and put it in the backlog, without waiting: it holds no change back. What they approved stays as it is unless they change it. You never widen what has to pass, not even when they leave it to you.
5. **Shipping.** When the trial passes, it ships the way the constitution says, as a change of that color with no brief: the person reviews it where the color asks for `person-review`, and its log closes the way the layer names, `gdd ship standing-checks --merge` or `--done <where>`.

## Later on

These go the same way, each as a backlog item with a log and a seal of its own name. Once the standing checks hold, `gdd color --paths` and the first `gdd brief` of a change name the ones it would go ahead of, under `setup_ahead`. Whether one comes first is yours to judge, by these lines:

- **A check the project hadn't set up,** which the color of a new zone asks for: `standing-checks-<check id>`. No change starts in that zone before it holds.
- **A check that waited for something to judge,** in a project that had no code: `standing-checks-<check id>`, right after the first item that brings it work. That item's checks role set up what the check needs, sealed with its tests, and its gates ran it; here it is proved and tried on that code, as steps 2 and 3 say.
- **A zone's own gate,** from the approved blueprint or from hardening: `gates-<zone>`, or `gates-<zone>-2` when the zone already has one. `gdd-checks` builds its check from the scenarios in `gdd/gates/<zone>.feature`, as soon as there is behavior to test. No further change starts in that zone before the check holds. The reviewer answers its rule from the first change.

A project prepared before version 0.3 has an item `gates-<zone>` for each zone instead. Those that are `done` stand for `standing-checks`, and each zone keeps the gates it has. Where one is still `todo`, ask the person whether to finish it, or to take that zone's `gates` out of the blueprint and set up `standing-checks`.
