# Preparing a new project

There's no code to learn from, so everything the agents need goes in the constitution: the stack, the tools and every command.

- **The stack.** If the request or the person names one, that is the stack, and the constitution uses it as named: in one run the request named a language and the constitution chose another. If not, propose what is usual for that kind of product, from what you looked up (`research.md`), with the reason in one line, and let the person choose. It comes before the checks, because they are set up for it: in one run, with no stack chosen, a check on new dependencies had to guess every format a manifest could take, and each review found one more.
- **The zones.** Propose them from what the product will do, before any code exists: money, accounts, personal data, what talks to outside services, deployment. Ask only what would change a zone or a gate. `gdd zones` says that pathspecs naming folders not there yet match nothing: here that is expected, so check only that each one is written as you mean it.
- **The commands from day one.** The commands to build, test, lint and scan for secrets are in the constitution before the first function exists, and CI runs each one once it has something to judge, so every check runs out of the agents' reach from the change that brings it work.
- **Only the checks that have something to judge.** Gates start at the minimum and grow, and with no code the minimum is `seal` and `secrets`: `standing-checks` sets up and tries those two, and CI running them, and nothing else. Every other check stays in the blueprint with its command and a `when` that names what it watches, such as `when: [':(glob)src/**', ':(glob)tests/**']` for the tests, and asks nothing of a change until there is something for it to reject. Nobody is asked to demonstrate a check on code that does not exist: in one run, the checks' setup stopped after 37 seconds on entry points of the product that weren't there, and its trial stopped on the same thing three times over, no source to compile, no tests to run, no screen to drive. The first change that brings what a check watches carries what the check needs to run: its checks role sets up the runner or the configuration its tests need, sealed with them, and that change's gates run the check for real.
- **The backlog.** Its first item, `standing-checks`, sets up the seal and the secret scan and CI, and says so in its line. Then advise where to start: functions with little risk first, so the checks get tried where a mistake is cheap, and money only once they have held. Each check that waits gets its trial as an item of its own, `standing-checks-<check id>`, right after the first item that brings it something to judge: there it is seen to reject a planted bad case, to accept without it and not to be switched off by a change. The backlog's order is the order of the work, so add the item first and its trial after it: `standing-checks`, then `catalog-page`, then `standing-checks-tests`. In one run the trials were added before the first item with code, and the next thing to do was to try the tests of a project that had none: the layer now refuses a trial added before any item of the product. Add each item with `gdd backlog add`, after reading its `--help`, and see that `gdd backlog list` reads every one before you ask for the approval: in one run, the layer didn't read the first item of a backlog written by hand, and it cost an approval.
- **What the person is told.** In the message that asks for the approval, the line on what isn't set up yet says how it goes here, in one sentence and in their words: "At first only two checks get set up and tried, the scan for secrets and the one that sees that nothing that judges a change was touched; the others start judging as the first changes bring them code." The template's own line, "the checks are written but not set up", is for a project that already has code: in two runs out of two it was copied as it was, and the person wasn't told that most checks would wait.
