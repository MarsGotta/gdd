# Designing the GDD skills

These notes record what has been decided about the skills, and why. The Manifesto is the reference: if anything here contradicts it, the Manifesto wins.

## What the skills are for

They let an agent apply GDD in any project with what the project already has (tests, linters, CI, git, branch protection), before any engine exists. The biggest benefit comes from engines, which enforce the method and automate it. The skills bring the method itself, so agents can work with the idea while engines get built.

## Decisions

1. **No scripts.** GDD is an open method, so the skills are instructions only. They use the tools a project already has and install nothing.
2. **The core of any engine.** The skills say what has to happen and who decides. An engine, T-minus or any other, loads them as its core and only adds how it does things: computing the color, sealing checks, launching agents. Never the other way round: if an engine needs the method to change, the change happens here.
3. **One skill per role, plus an entry skill.** Engines launch agents by role, and each agent loads only the skill of its role. An entry skill guides the four moments: Prepare, Brief, Execute and Harden.
4. **No models or providers.** The skills recommend by what a task needs, never by name:

   | Level | What it means | For |
   |---|---|---|
   | light | little reasoning, cheap and fast | mechanical work and green changes |
   | standard | normal reasoning | yellow changes and orchestrating |
   | deep | the most reasoning | red changes and checks that are hard to write |

   Each project says in its blueprint which model is each level. One recommendation does come from the method: the reviewer should be from a different model family than the agent that did the work, whenever possible, which `gdd-prepare` proposes where the person has one and the blueprint's `reviewer` records (decision 34).
5. **Context: almost all per gate, a minimal core across the flow.** The cross-cutting context goes into every call, so it has to stay small, and the agent that passes a gate never sees its hidden examples or the conversation where its checks were made.

   | Layer | What it carries | Where it lives | Who loads it |
   |---|---|---|---|
   | Cross-cutting | A few lines: the project uses GDD, each role edits only what it owns, a sealed file is never touched, gates are passed with facts, when something doesn't fit you stop and say so, and a map of the files | The GDD block in AGENTS.md, which imports the constitution, written when preparing | Every agent, always |
   | Per gate | The skill of each role, and the context the blueprint gives that gate | Given to each agent when it is launched for its gate | Only the agent of that gate |
   | What the previous gate left | The brief and the sealed checks, on the seal, and the log, which the orchestrator keeps | Files in the repository | The next gate, as part of its context. The builder never gets the log (decisions 23 and 24) |

   The constitution holds only what applies everywhere. A rule that belongs to one zone goes into that zone's context in the blueprint, so it reaches only the gates that need it. An engine does this split on its own. Without one, the orchestrator does it when it launches each agent, and its skill has to teach it how.
6. **Everything in English.**
7. **Seven skills.** One entry skill and six more, each for one role in one moment:

   | Skill | Who loads it | Moment | Reads | Leaves | Level |
   |---|---|---|---|---|---|
   | `gdd` (entry) | The orchestrator | Guides all four | The request, the blueprint and where each brief stands | What comes next, who is launched and with which context | standard |
   | `gdd-prepare` | The orchestrator, with the person, at the start or when the project changes | Prepare | The repository and what it already has (tests, CI) | The blueprint with its standing checks, the constitution, the GDD block in AGENTS.md and the protections (branches, CODEOWNERS) | deep |
   | `gdd-brief` | The orchestrator, for each change | Brief | The request and the blueprint | The brief: the scenarios that say what has to pass, the expected color and the gates with their context | standard |
   | `gdd-checks` | Another agent, never the one that builds | Brief, and after Prepare and Harden | The brief, or the standing checks to set up | Checks that fail for the right reason, proof that they can pass, and their seal | by color |
   | `gdd-build` | The agent that passes the gate | Execute | The brief and the sealed checks | The change and the facts that prove it | by color |
   | `gdd-review` | The reviewer, with a clean context | Execute | The change, the blueprint and the checks, never the conversation | The verdict and the recomputed color, with the evidence of the checks it ran itself | by color, on the blueprint's `reviewer` models where it has them |
   | `gdd-harden` | The orchestrator, with the person, when something slips through or a gate adds nothing | Harden | What slipped through and its brief, or the logs of the gate | The crack, the scenario that would have caught it and the blueprint change, or the removal, for the person to approve | deep |

   Building is split in two. `gdd-prepare` decides with the person which gates the project needs and the standing checks that demonstrate them, one list for the whole project, but sets up nothing. `gdd-checks` builds both kinds of checks: after preparing, the project's standing checks, once, and after hardening, the check of a gate a zone was given (decision 33); when briefing, the checks of each change. `gdd-review` then tries each new standing check on purpose, once, and no change starts until they hold.

   Proportion lives in `gdd-brief`: the color comes from what the change touches (decision 14), and it decides which checks are needed and at which level. `gdd-checks` applies the same proportion: green keeps the existing checks, yellow adds a test for each scenario, each one broken on purpose before it's sealed, and red adds mutation testing where the stack has a tool for it. Hidden examples written by another hand join red only from `platform` up (decision 23).
8. **A shared log for metrics, no extra skill.** Each brief has its own log, `gdd/log/<id>.jsonl`, where `gdd` appends one event when each step closes. Each role that runs as its own agent ends its work by reporting what only it knows: the skill and its version, its result and what it caught. `gdd` adds the level, the round, and the time and tokens when its environment provides them (decision 25). `gdd-harden` reads the logs to see what slips through, which piece catches what and what each role costs, so a project can compare itself with itself. An engine fills the same logs on its own, with exact figures. One file per brief keeps branches from colliding when they merge. Its format is part of the contract (decision 13).

9. **Preparing, from an idea.** `gdd-prepare` works as a guided conversation, from "I want an online shop for cat products" or from an existing repository.
   - It proposes first and asks afterwards: "for a shop, these are the usual zones; correct what doesn't fit". It asks only what changes a zone or a gate (payments, accounts, regulated products, the stack), and when the person doesn't know, it proposes what is usual for the sector.
   - In an existing project it starts with a complete analysis: stack, structure, tests and what they cover, CI, linters, dependencies and their health, security findings and documentation, with existing code mapped to risk zones. Complete means it covers everything, not that it reads every file: deterministic tools do the counting (linter totals, coverage, dependency audits) and the agent reads their summaries. If there is nothing yet, it is the greenfield path.
   - It asks, in any project, for external references that enrich the context: designs (Figma), MCP servers, documentation, templates, API specifications, brand guides. Each one is kept as a copy with its source and date, and the blueprint says which gate needs it, so it doesn't become cross-cutting by accident. MCP servers get the least access their gate needs.
   - It may research similar products and the sector's rules, only with proven sources (official documentation, the regulation itself, the vendor's own pages before third-party posts), always cited and kept as copies. That helps the person decide; the person decides, and it is not legal advice.
   - It leaves three documents in the repository:
     - **the constitution**: the stack, the tools and the commands to build, test and lint (whatever the agent can't deduce from the code, and in a new project, all of it), plus the rules that hold everywhere (prices in cents). A rule of a single zone, such as never storing card data, goes to that zone instead. Every agent reads the constitution before working (decision 13);
     - **the blueprint**: risk zones as git pathspecs, the checks of each color, their context and the model levels, in Markdown with a Mermaid diagram, so the person sees it drawn and agents read it as text. An interactive page can be generated from it on request, never the other way round. No PDF;
     - **the backlog**: the functions to build, each with its expected color. The roadmap, when wanted, is the same backlog ordered in phases. Functions change often; risk zones rarely do, so the blueprint stays stable because it holds no functions.
   - The person approves the first blueprint, and the approval stays written: a commit or a pull request of theirs, with the blueprint protected by CODEOWNERS.
   - In a new project, the first item of the backlog is setting up the standing checks. Then it advises where to start: low-risk functions first, and money only once its gates have held.
   - A change that touches something no zone covers is never green: `gdd-brief` judges it, writes down why, asks when it can't tell and proposes the update of the blueprint, without stopping the change (decision 36).
10. **Known debt never blocks, and never grows.** In an existing project, what already fails a check (lint errors, low coverage, an outdated dependency) is recorded as known debt with its baseline in `gdd/debt.md`, and becomes an item of the backlog with the color of its zone, where `gdd-prepare` may recommend a refactor. Gates don't block that debt, but they block any new debt: a baseline may only go down, and lowering it needs no one's approval. Recording something as debt loosens a check, so the person approves it, as part of approving the blueprint; it never happens on its own. A test that fails today is debt too, visible in the backlog and the log, never silently skipped.
11. **Deterministic first.** Whatever something deterministic can check is checked that way: it costs no tokens and always gives the same answer. When proposing and building gates, climb this ladder and stop at the first step that works:
    1. what the stack already brings: types, a linter rule, the test runner;
    2. a mature open-source tool with a solid community or company behind it;
    3. a small script of the project's own, only when nothing exists: simple, nothing it doesn't need yet, protected like any other check, with its bad case and the practices of decision 16;
    4. a new or less proven tool, only with a notice (how old it is, who maintains it, its license, what it does with your data), and the person decides;
    5. when nothing deterministic works, the reviewer or a person.

    The skills ship no scripts: they recommend that projects use their own.
12. **Reporting progress, briefly.** By default `gdd` tells the person one line per gate (passed or failed, and in how many rounds), the detail only when something fails or the person has to decide, and a summary at the end. Everything else goes to the log.
13. **The contract.** What the method leaves in a repository is the contract between the skills and any engine, T-minus included: an engine reads and writes the same files. Its version (`gdd/1`) goes in the front matter of the blueprint and of each brief, and in every log event. It is still `gdd/1` after the changes of decisions 20 to 28.

    | File | What it holds | Who writes it | How it changes |
    |---|---|---|---|
    | `AGENTS.md`, GDD block | The cross-cutting core, in under 100 words, and the map. It imports the constitution with `@gdd/constitution.md` (Claude Code imports it; for other agents it stays a path to open) | `gdd-prepare` | With the person's approval |
    | `gdd/constitution.md` | The stack, the tools, the commands to build, test and lint, and the rules that hold everywhere | `gdd-prepare` | With the person's approval |
    | `gdd/blueprint.md` | Zones as git pathspecs with their color, the standing checks and which of them each color asks for, the context of each gate and the model levels, in YAML front matter, plus a Mermaid diagram | `gdd-prepare`, `gdd-harden` | Protected by CODEOWNERS; the person approves |
    | `gdd/gates/<zone>.feature` | A zone's own standing gates, in Gherkin, when the person asked for one or hardening gave it one | `gdd-prepare`, `gdd-harden`, with the person | Like the blueprint |
    | `gdd/backlog.md` | The functions to build, with their expected color, in phases if wanted | `gdd-prepare`, `gdd-brief`, `gdd-harden` | Freely |
    | `gdd/debt.md` | Known debt, with the baseline of each check | `gdd-prepare` | Down freely; up only with the person's approval |
    | `gdd/briefs/<id>.md` | What has to pass for one change: the scenarios it adds or changes, what it touches, its gates and its expected color. The person approves it when its color asks for `brief-approval`. No status and no seals | `gdd-brief` | Never once its hashes are in the log: a change makes a new version, which goes back to the person only if its color asks for `brief-approval` and what has to pass changes |
    | `features/<capability>.feature` | The scenarios of changes, grouped by capability, each tagged with its brief and with an id that its test cites | `gdd-brief`, with the person | Only through a brief |
    | `gdd/log/<id>.jsonl` | Everything that happens to a brief, one event per line: the approval with the hash of what was approved, each seal, the color computed and why, each gate's result with its evidence (command, exit code and last lines), the verdict and any waiver | `gdd`, from what each role reports | Only appended |
    | `gdd/context/` | Copies of external references and research, each with its source and date | `gdd-prepare` | Refreshed with a new date |

    The seal of a change is a git ref the builder never writes to, and hidden examples exist only where the builder's credentials can't read them (decision 23). A green change has no brief file, unless the blueprint's green asks for `brief-approval`: it passes the existing checks, and its events go to a log like any other. If the project has a CLAUDE.md, `gdd-prepare` adds `@AGENTS.md` to it, because Claude Code reads AGENTS.md only when there is no CLAUDE.md.
14. **The color: git sets the floor, and judgment can only raise it.** Both parts, always together:
    - **Deterministic.** For each zone, an exact command on the change, such as `git diff --name-only <start> HEAD -- ':(glob)src/payments/**'`, and one more that excludes every zone to find what none covers, which is never green (decision 36). It gives the same answer every time, costs no tokens and needs no script. It counts what the builder did: the brief, the scenarios and the sealed checks are in the seal, before `<start>`, and don't count (decision 24).
    - **Judgment.** Then the agent looks for what the paths miss: code that a delicate zone imports, configuration and environment, dependencies and lockfiles, migrations and data, permissions and feature flags, build and CI files. It may raise the color, never lower it, and it writes its reason in the log.

    `gdd-brief` does both when briefing, on what the change will touch; at the end, `gdd-review` does them again, with a clean context, on what it actually touched. If the color rises, the change stops and goes back to Brief: `gdd-checks` adds what the new color asks for, and the person approves the brief again if that color asks for `brief-approval`. The new checks are written from the base, without reading what was built: a test written after seeing the code catches less. Only a blueprint change approved by the person can lower a color, because that is loosening. When `gdd-harden` sees the same reason come back, or a judgment that caught something, it proposes turning it into a pathspec or a zone: what judgment finds today, git checks tomorrow.
15. **Gates are written in Gherkin.** The standing gates of a zone are written with the person in `gdd/gates/<zone>.feature`, by `gdd-harden` when something slipped through there, or by `gdd-prepare` when the person asks for one (and no longer for every zone: decision 33): one `Rule:` for each thing a gate demonstrates, and under it at least the scenario its check must reject (the bad case) and one it must accept, each tagged with the check that covers it.

    ```gherkin
    @zone:payments
    Feature: Payments gates

      Rule: Card data is never stored

        @check:no-card-data
        Scenario: A change that saves a card number is rejected
          Given a change that writes a card number to the orders table
          When the gate runs
          Then the no-card-data check fails and names the file and the line

        @check:no-card-data
        Scenario: A change that saves only the payment token passes
          Given a change that writes the provider's payment token
          When the gate runs
          Then the no-card-data check passes
    ```

    The person approves them with the blueprint, and changing them is changing the blueprint. They are the reference for everyone who touches a check: `gdd-checks` builds each check from its scenarios, at whatever step of the ladder, and proves it fails for the right reason by running it on both cases; `gdd-review` uses them to plant the bad case and to judge a check that fails; and the agent that passes the gate reads them to understand why a check failed, never the hidden examples. The same language describes what must pass, from the gates of a zone to the scenarios of a change.
16. **Good practices for the project's own scripts.** When the ladder reaches step 3, the script is a check like any other. These rules live in `gdd-checks`, and `gdd-review` judges scripts by them:
    - one job, written from the scenarios of its gate, with the bad case as its first test;
    - deterministic: the same input gives the same output, with no network, clock or randomness;
    - never interactive: everything comes in through arguments, environment variables or stdin, and `--help` says what it checks, how to run it and which scenarios it covers;
    - exit code 0 when it passes and a documented code for each kind of failure; when it fails, it names the file, the line and the rule, so it fails for the right reason;
    - results to stdout, structured when something else reads them, diagnostics to stderr, and output short enough that an agent's environment doesn't cut it;
    - it handles its own errors instead of leaving them to the agent, and every value comes from the blueprint or says why it has that value;
    - only the languages and tools the project already uses; a new dependency is pinned and goes through the ladder;
    - it reads only what it needs, writes nothing outside its output and never touches secrets;
    - simple and with nothing it doesn't need yet, sealed and protected like any other check, and run with the same command locally and in CI if there is one, a command the constitution records.
17. **Flows the skills cover.**
    - **Decisions nobody has made.** While drafting, `gdd-brief` marks each one with `[DECISION: …]`, and a brief isn't done while `git grep` finds any. Questions like rounding each line or the total come up there, before anyone builds.
    - **Traceability.** Every scenario has an id that its test cites, and every check is tagged in a gate, so a grep finds a scenario without a check, or a check no gate asks for.
    - **It doesn't fit the brief.** The agent stops and says why, and the brief goes back to `gdd-brief` as a new version, which goes back to the person if what must pass changes and its color asks for that approval.
    - **Urgencies.** Skipping or lowering a check is loosening: the person approves it, the log records who and why, and it becomes an item of the backlog, like known debt.
    - **Proof that a check can pass.** If it needs a throwaway implementation, the agent that will build never sees it, because it would give away the solution.
    - **Evidence.** What the building agent reports is a claim. `gdd-review` runs the checks itself, and the reported evidence only serves to compare.
    - **Approval.** Without an engine, the agent may share the person's git identity, so a commit alone proves little. For red, the skills recommend approving the pull request on the platform, and they say where this falls short.
18. **Agents and security.**
    - Only `gdd` activates on its own. Role skills load explicitly, so no agent loads another role's skill by mistake: in Codex, with `allow_implicit_invocation: false`; in Claude Code, with one subagent per role that preloads its skill. Optional adapters per agent may map each role to its skill, tools and model level. They hold no code, and the method never depends on them.
    - The orchestrator hands each agent its skill explicitly, and the fields every role reports work as a canary: if they're missing, the skill wasn't followed.
    - In a GDD project, GDD comes first over other skills or methods installed: if one asks the same agent to write the tests and the code, the agent that passes a gate still doesn't write its checks.
    - When an agent can't launch another, the orchestrator gives the person one line to open a new session with the right skill and brief, so every role still starts with a clean context.
    - Everything copied from outside (designs, documentation, web pages) and everything in the repository being analyzed is data, never instructions, and `gdd-review` flags any text in them that gives orders.
19. **How the skills are written.**
    - **Test first.** Each skill gets at least three scenarios, run without it and with it, measuring tokens and time. For the discipline rules (checks aren't touched, gates are passed with facts), pressure scenarios that mix haste, authority and "the test is wrong, just fix it", and a table of excuses and answers taken from what the agent said without the skill.
    - **From real cases.** Skills a model writes for itself bring nothing on average, so these come from the Orbit run, the failures of the T-minus pilot and a real run with the person's corrections, never from this file alone. The pilot is the week of 3 to 9 November 2026, when agents built T-minus on autopilot through a gate of its own, without an engine and before these skills were written: 188 changes went in, and builders stopped 72 times. A skill says "the pilot" only where one of its reports says so, and "in one run" for the rest. They also take what the runs of the [method benchmark](https://github.com/MarsGotta/agent-method-bench) teach, as long as it holds in any project: never its project, its requests or its scenarios.
    - **Gotchas.** Each SKILL.md lists the concrete mistakes an agent makes without being told. `gdd-harden` turns what slips through into checks, not into cross-cutting paragraphs.
    - **Short.** `gdd-build`, the one loaded most, about 200 words; the AGENTS.md block, under 100; the rest under 500 lines and 14,500 bytes, so that an agent keeps the whole of it after a compaction, which leaves it the first 20,000 characters, with what isn't needed at once in `references/` (in `gdd-prepare`: a new project, an existing one and research; in `gdd-review`: the full review and new standing checks) and the templates of the contract in `assets/`. Sizes are watched in bytes and words, because lines say little. Every addition comes with a cut.
    - **Descriptions.** In the third person, saying when to use the skill and never summarizing its steps, because an agent may follow the summary and skip the body. Under 400 characters for every skill but `gdd`, the only one found by its description: the others are loaded by name, and every description is paid on every turn. Trigger tests only for `gdd`: about twenty requests, half of which must not trigger it.
    - **At all three levels.** The same text behaves differently on a light model, and `gdd-build` runs light on green.
    - **Most effort on verification.** `gdd-checks` and `gdd-review` are the skills that improve results the most.
    - **One source for the contract.** It lives in `skills/CONTRACT.md`, and a check in this repository keeps each skill's templates in line with it. A second one runs the git commands the skills give in a throwaway repository, with the cases that slipped through once. The skills still ship no scripts: those checks are ours, not something a project installs.

20. **Where a person approves is in the blueprint.** The team always approves the blueprint, and anything that loosens it. Every other approval is a check of type `person` that a color carries or not, so each project sets how strict each level is: `brief-approval`, the person approving what has to pass before anyone builds, and `person-review`, the person reviewing the change at the end. The template proposes the first on yellow and red and the second on red, and `gdd-prepare` presents them as a proposal. A change whose color rises goes back to Brief, and a new version of a brief goes back to the person only if its color asks for `brief-approval` and what has to pass changes. This follows the Manifesto from version 0.8 on: the colors are levels of strictness, and the blueprint says where a person approves.

21. **Licenses.** The skills and the scripts are under the MIT license, and each SKILL.md says so in its front matter. The Manifesto and the website's texts are under CC BY 4.0. Both are at the root of the repository.
22. **What the log needs so the method can be measured.** The website asks for three notes from the first day: how often a change stops a person, how long it takes to go out and what slips through. The log only had the last one. So an `ask` event marks the moment something starts waiting for a person, a `ship` step closes the log of a change, each finding of a review gets an `id` and is closed later with how it ended, `limits` gains a cap on tokens for the environments that report them, and the body of the blueprint holds the baseline and the figure that would make the team simplify. Nothing else was added: what slips through by color comes from crossing `harden` with the color already in the log. The template's limits (six rounds, two hours and four hundred lines per change) are provisional, until the pilot's figures replace them.
23. **The seal is a ref, and the blueprint says how far out of reach it is.** The website sealed a change in a branch only the person writes, and the skills sealed it in a commit on the builder's own branch. Now both are the same thing: a git ref, `gdd-seal/<id>`, that the builder starts from and never writes to. The blueprint's `guarantee` says who can write to it: on `rule` nothing stops the builder, on `platform` a ruleset and credentials of its own do, and an engine holds it itself. `gdd-prepare` sets it after a probe that tries, from the builder's environment, to push to the main branch, write to a seal, read the hidden examples and find a credential it shouldn't have. What was pure git in the review became a machine check, `seal`, that every color carries. Hidden examples left the default red: on `rule` the builder could read them, so they exist only from `platform` up. The builder no longer gets the log, which names the commit of what it must not see.
24. **Where each thing is committed, and what every comparison is made against.** No skill said who commits what, and three failures came from it. The review recomputed the color on everything changed since the base, which includes the brief, the scenarios and the sealed checks: no zone covers them, so every change with a brief rose to red. The seal was compared with the name of its ref, which a builder can move on `rule`. And a green change, with nothing sealed, had no ref to compare with. The contract now says four things that have to be true: what judges a change is committed on `gdd-seal/<id>` before anyone builds, and its tip is `<start>` (the base when nothing was sealed); the builder commits on a branch of its own that starts there; every comparison is made against the commit `<start>` written in the log; and the log and the backlog are the orchestrator's bookkeeping, kept in its own copy and committed on top of a change that is about to ship. The seal moves forward with new commits (a new version of a brief, new checks, the main branch merged in before the change ships), and its tip is always `<start>`: merging the main branch straight into the change would bring other changes' briefs into the comparison. The `seal` check became one exact command, the same in every project. On `rule` a builder that shares the repository can still fool the command itself, so the reviewer runs it in a fresh clone and compares each sealed check with its blob hash in the log.
25. **The orchestrator does Prepare, Brief and Harden itself, and completes every report.** Those three need the conversation with the person, so `gdd` loads their skills and does them, and they carry no report block. They need the deep level, and the orchestrator says so to the person when it isn't on it. The three roles that run as their own agent report three fields, the ones only they know. Level, round, time and tokens are the orchestrator's: a role asked for them would make them up, and many environments give the orchestrator the exact figures of each agent it launches.
26. **The short review, and what gets split.** What a role's skill carries is paid whole on every launch, with a cold cache; what the orchestrator loads is paid once per session. So only `gdd-review` is split: its body holds what every change needs (the color and the seal), which is the whole review of a change whose color doesn't ask for `review`, and `references/full-review.md` holds the rest. The condition to read it is in what the reviewer was given, and a `pass` without what was run doesn't count, so a reference left unread shows. Nothing else is split: a reference that isn't read when it's needed costs more than the tokens it saves. What saves most isn't text. Evidence is five lines at most, the output of a command goes to a file, `gdd-harden` counts with `grep` before it reads a log, and every fix round is a new agent.
27. **What the walk-throughs closed.** Four changes were followed step by step through the skills, by a reader who hadn't written them. What came out: a path no zone covers is asked about once (classify it now, or go on as red); a change also passes the standing gates of every zone it touches, whatever its color; the color the reviewer found goes in a line of its own, `COLOR:`, so no verdict has to carry it, and `stop` wins over anything else in its answer; a failed `seal` check stops the change at the gates as it does in the review; a `CANNOT:` about a check goes to `gdd-checks` and not to the brief; an approval says in `where` how the person approved, and without a platform that is a rule and not a guarantee; the blueprint says beforehand what an emergency may skip, and the change goes through it afterwards, as the core of the method asks; building a zone's gates has a log and a seal of its own, and ships like a change; the checks of the standing gates are a red zone; and a `harden` step goes to the blueprint's log, naming the change that let the failure through. A second reader then walked the same four changes over the rewritten text, and what it found went in too: the update through the seal, the bookkeeping, the fresh clone, and a short review that also looks at the tests that were already there.
28. **What was still open before testing the skills.** The reviewer's exam runs: a question is the change as it shipped, two commits of the main branch in `gdd/exam.md`, so nothing is stored apart. A reviewer is examined on a fresh clone at that change, a good change or two keep one that rejects everything from getting full marks, and each run leaves an `exam` step in the blueprint's log. CI, where there is none, is the first item of the backlog, and `gdd-checks` writes it, because the agent that builds doesn't set up what judges it.     - The two cases measure the final message with a pattern, its length and whether it names a branch or a commit, beside the LLM judge, which fails a message without saying by how much.

    The contract stays `gdd/1`.
45. **The constitution carries the product's rules, and a brief asks seven questions before its first scenario.** In one run of the method benchmark, the brief of the payment change said it wouldn't touch stock, because orders were a later item of the backlog. The person approved it without being able to judge it, and everything the change's checks looked at passed, while paying took no product out of stock. In the same benchmark, another method's constitution, written from the project's data, carried a rule about stock, and its specification inherited it. The method missed nothing it checked: it missed what its brief never wrote down, because a brief started from the paths of the change, and the paths say where a change lands, not what it does to the rest of the product. So:
    - The constitution carries what must never happen in the product, whichever part a change touches, in the person's words: three to seven rules, which `gdd-prepare` proposes from the project's data and what it looked up, and the person corrects and approves with the blueprint. Seven at most, because the constitution goes into every call and every brief goes through each rule. How one zone's code is written stays in that zone's context. A rule brings no check of its own: it becomes a scenario of each change that can break it. What stays out is that other constitution as it is, with its rules in capitals and its governance, and gates of a zone written by an agent, which decision 33 ended.
    - On yellow and red, before the first scenario, `gdd-brief` answers seven questions: the product's rules, and what can go wrong in every zone whose data the change changes, not only where its paths fall; what it leaves behind, seen from another part of the product; the features it reads or changes, and what their briefs left for later; what happens twice, or from two places; the rule the person would have an answer for; whether the product still tells the truth while a part waits for later; and what it won't do, told as a consequence the person can weigh, in a new section of the brief, "What it won't do yet". The reviewer's reading of a brief (decision 47) asks the same seven, and `scripts/check_skills.py` checks that the two lists stay the same.
    - Its author set how much of this reaches the person. What they read to approve stays under 150 words: what the change will do, the rules of the product it touches and up to three consequences of what it won't do yet. A change asks no question on green, one on yellow and two on red, and a rule of the product the person leaves to the agent takes what is usual in its sector, told in the last message as an assumption they can still correct. A request is split only when it would go over the blueprint's lines or cross two red zones, the split goes to the person before any part is briefed, and its first part has to show them something.

    The contract stays `gdd/1`: the constitution's section and the brief's new one are text, and no field changed.
46. **A change goes through its checks in two tiers, and each color has limits of its own.** Its author asked for less time per change without weaker gates, and decided where a project starts. In one run of the method benchmark, a payment change passed its tests at the first try and then spent more rounds raising its mutation score to the highest, the number Prepare had set. In the same benchmark, a booking change went through gates of several minutes round after round, because every check ran in every fix round. So:
    - Each check says when it runs. Each round, on every color: the seal, the tests of the change, lint and types and the secret scan, under two minutes together. Once, before the reviewer: what takes longer, such as one browser test of what the change touches when it touches what a person sees, under ten minutes in all. A check that takes longer than its tier allows moves to the second, and a run past its time counts as it came out and goes to the backlog for hardening, never cut off: what is slow is the check, not the change.
    - Mutation testing and thresholds of coverage left the minimum. Hardening adds them when the tests proved weak, at the tool's own default, looked up on the tool's own page: a number for a tool is never written from memory.
    - The order of a change is told wherever its flow is, because a list of checks didn't show it: the brief writes its use cases as scenarios in Gherkin, the tests of the change are written from them, one for each, seen failing and sealed, and only then is it built. Those are the tests a blueprint means. A green change has no brief and no scenarios, and runs the checks that already exist.
    - The caps of a change are in each color. Green, yellow and red start at 10, 30 and 60 minutes of work, 1, 2 and 3 fix rounds, and 1, 2 and 2 runs of the second tier, until the project's logs correct them. The person approves the brief only on red: on yellow the brief and its scenarios are still written, the person is told in a line what the change will do, and nobody waits for them. They, or their team, can ask for that approval on yellow too.
    - Light is for green, standard for yellow and for building on red, deep for preparing, hardening and the brief of a red change. The reviewer runs at the level of the change, on the same family of models, and on another only once it was seen to work when preparing, which turns around the recommendation of decision 4.
    - What `gdd-prepare` opens before it proposes a gate is a reference, `references/gates.md`, with these starting points, how to read what the project already runs and the ladder. A second one, for the web, says what usually goes wrong there and the traps of setting its tests up, and `gdd-checks` carries a copy.

    The contract stays `gdd/1`: `runs`, the seconds of each tier and the `limits` of each color are optional, and a blueprint without them reads as it did. Decisions 49 and 50 later changed what this one says of yellow: the person approves its brief again, and it starts at 45 minutes and 3 fix rounds.
47. **The reviewer reads more, runs less, and reads the brief before anyone builds.** In one run of the method benchmark, a reviewer sent a change back round after round, each time for a real defect finer than the last, and the change took over four hours. And what the method missed in that benchmark was in the brief, not in the code (decision 45). So:
    - On yellow the reviewer reads the change against its brief without running it, in one round of about five minutes. On red it runs the change and tries to break it, two rounds at most of about fifteen minutes, without running the gates again: the orchestrator already ran them out of the builder's reach, and the log has what came out.
    - Only what breaks a scenario of the brief, a rule of a zone the change touches or a rule of the constitution sends it back. The rest, the design of the code included, goes under `LATER:` and to the backlog, on every color, because the change works and another round costs more than the item. Its author chose that over keeping design as a `fix` on red.
    - Before anyone builds, on red and on yellow when the change changes data another zone owns, a reviewer reads the draft brief with the seven questions, runs nothing, and what it finds reaches the person with the approval, or the log where nobody approves. It is a `reading` step, optional in the log.

    The contract stays `gdd/1`. Decision 50 later gave the reviewer two rounds at most on yellow.
48. **A limit stops the change, and the project can count it.** In one run of the method benchmark, a cap on rounds stopped nothing: the orchestrator counted by hand and went on past it. In one run, the person answered "you decide", and the orchestrator came back to ask for more rounds again and again. In one run, every limit that ran out was lifted with a waiver written down as the person's, after words like "go on" or "approved, the rest you decide", a reviewer's `stop` among them. And in one run, hardening started in the middle of a request and opened more red changes. So:
    - A second script travels with the skills, as decision 42 left room for: `assets/limits.sh`, which the project copies to `gdd/limits.sh` and owns, like the runner, a choice of its author's over running it from the skill's folder. It reads the blueprint and one change's log, says what the change has left of each cap of its color and whether a tier of checks took longer than its seconds, and writes nothing. The orchestrator runs it before each round and each run of the gates, and `scripts/check_commands.py` runs it on sample logs.
    - When a limit runs out the change stops. If the person had left the decisions to the agent, nobody asks them to extend it: the change is split or left in the backlog. Going past a limit is a waiver, and a yes counts only for a question that names what it loosens, what was spent and what more buys: "go on" isn't one. A reviewer's `stop` is never waived: it gets a fix and a new review.
    - Hardening never starts by itself. A change leaves one proposal at most in the backlog, and hardening happens between changes, when the person takes it up.
    - Two touch-ups. Before a message goes to the person, the orchestrator takes out any file of the method named to justify a question, because in one run it kept quoting a skill's path. And a check that closes at a number starts from the tool's own default, looked up, because in one run Prepare wrote the highest.

    The contract stays `gdd/1`: the counter is optional, and the check of this repository lets it through, with the runner, as the only scripts the skills carry. Since decision 53 the layer counts the limits before each round and each run of the gates, and the counter stays as the project's own reading of them.
49. **The person approves the brief on yellow again.** Decision 46 left the approval of a brief to red, so that a yellow change waited for nobody. In one run of the method benchmark, a yellow change lost one of its scenarios, twenty products a page, which the person had caught whenever they approved a yellow brief, as version 0.9.1 asked. Every check of the change passed, because what has to pass never said it, and only the person could see that it was missing. So:
    - The template carries `brief-approval` on yellow and red, and `person-review` on red, and `gdd-prepare` still presents them as a proposal. The person, or their team, can take the approval off yellow: then the brief and its scenarios are still written, the person is told in a line what the change will do, and nobody waits.
    - The message that asks for it is one instruction for both colors, in the body of `gdd-brief`: under 150 words, in the person's language, what the change will do, each scenario in one line in their words, the decisions the agent took marked as its own, and one question a yes answers. Red adds the rules of the product it touches and up to three things it won't do yet, with its scenarios beside the message as they are. It comes as a template with an example and a check before sending, which counts the words, looks for a line for every scenario and writes the `ask` event, because decision 44 showed that shape is what an agent follows.
    - What the person approves is in front of them. In a project a person built with 0.10.0, the scenarios were sealed on `gdd-seal/<id>` and written in a copy git ignores, so from the main branch the person couldn't open them in their editor or on the platform until the change's merge request, and read them only by asking to have them pasted into the conversation. An approval is only worth what was seen, so the orchestrator now writes the brief and its scenarios in its own copy, the one the person has open, at the paths they will have in the project, and seals them from there. The seal is still what judges: after sealing, the orchestrator checks that each visible file has the hash it logged. An edit the person makes there is a correction, which makes a new version of the brief, and when the change goes in, the visible copy gives way to the main branch's: the orchestrator never commits those files on the main branch itself. Its author proposed it, from that project.
    - A case asks for a yellow change in a shop with the template's defaults, measures the message with a pattern beside the judge, and looks for the brief in the person's copy.

    The contract stays `gdd/1`: only the template's colors changed, and where the orchestrator writes a brief before sealing it.
50. **A finished build is always judged, and yellow has more room.** In one run of the method benchmark, a yellow change spent its two rounds on a clash with an older test. Its last build was finished, the project's counter said no room was left, and the orchestrator stopped without running its gates: the change stayed built and never went in. A cap is there to ration rounds of fixing, and that one stopped the judging of work already done. In the same benchmark, two rounds were too few for yellow. So:
    - A cap that runs out stops the next round, never the gates or the review of a build already finished. `gdd/limits.sh` reads where the change stands from the last of its build, gates and review steps: a build that didn't stop waits for its gates, gates that passed wait for the review, and a review that passed waits to ship. Then the caps on rounds, on the times sent back, on minutes and on tokens are printed with what was used and stay out of `stop`, a line says what to run next and that no new round starts after it while one of them has no room left, and the last line gains a field, `judge`, with what comes next. The runs before the review still stop a build that waits for its gates, because they would run once more. `scripts/check_commands.py` runs both sides: a log with its rounds spent whose last step is a build exits 0 and says to run the gates, and the same log after those gates failed exits 1.
    - Yellow starts at 45 minutes of work, 3 fix rounds in all, 2 for each gate that sends it back, and 2 runs of the checks before the review. Green and red keep theirs. On yellow the reviewer still reads the change against its brief in about five minutes, now two rounds at most. The minutes come from a project a person built with 0.10.0, where three of four yellow changes went past 30, one of them more than twice over.
    - The counter reads waivers. In that project every limit that ran out was lifted with the person's yes, and after the first waiver `gdd/limits.sh` kept saying there was no room, so the next ones were counted by hand. A `waiver` of a limit now carries two optional fields, `limit`, the key of the cap, and `to`, its new value for this change, and the counter takes that value, the last waiver of each cap winning, and says on the cap's line that a waiver raised it. A waiver still needs the person's yes to a question that names what it loosens, what was spent and what more buys.
    - Two cases cover it: one whose rounds ran out while a build waits for its gates, where the orchestrator runs them instead of stopping, and the case of decision 48, whose last build has already failed its gates, where the change still stops.

    The contract stays `gdd/1`: `judge` is one more field in a line agents read, `limit` and `to` are optional fields of a `waiver`, and a blueprint keeps the caps it has.
51. **How far the tests of a change go depends on its color.** In a project a person built with 0.10.0, writing and sealing the tests was most of the work. On one yellow change the agent that writes the checks broke its own throwaway solution by hand in 36 ways, about fourteen minutes, which the person took for a mutation gate, and it also added screen sizes nobody had asked for and repeated a test twenty times. Showing that a check closes is worth its cost where a failure is expensive, and a yellow change already has a reviewer who reads it against its brief. So, with the template's defaults, and the blueprint wins:
    - Yellow takes three steps of `gdd-checks`: the test written from its scenario, seen rejecting the code as it is, with two examples per scenario, and generated inputs only where the scenario states a rule for every input. No throwaway implementation and no break on purpose: a test is seen passing only when a correct version already exists or costs a line, and otherwise the report says for each check that it was seen rejecting and not seen passing. The reviewer's reading on yellow now looks for a test that would pass without its behavior, and names it as a check that is wrong, which goes back to `gdd-checks`.
    - Red takes the five steps, with one break on purpose for each check, the one that removes the work, and more only if that one stayed green.
    - On every color, nothing no scenario asks for: what looks missing goes in the report under `MISSING:`, for the orchestrator to take to the brief, never into one more test. The standing checks set up after preparing keep every step, because they judge every change.
    - `gdd-prepare`'s table of what a change may take gains a row for the change's tests, and a case gives the checks role a yellow brief and looks for tests sealed as seen rejecting, without an implementation.

    The contract stays `gdd/1`: the `proofs` of a `checks` step may lack the case that passes.
52. **Two touch-ups from the same project.**
    - A document no zone covered came out yellow, and the person had to ask for a zone of its own. `gdd-prepare` now proposes from the start a green zone for documents that don't change how the product behaves, unless the person says otherwise.
    - A reviewer in another environment was launched in the background with its command line and sat waiting for the keyboard until the person asked. The launches documented in the adapters and in the reference on levels close standard input, `< /dev/null`, and whoever launches a role checks within a minute that it started.

    The contract stays `gdd/1`.
53. **A layer keeps the order and the log, and the skills got shorter.** In a project a person built with 0.10 and in the method benchmark, the parts of GDD that take judgment held, and the bookkeeping, done by a model following text, failed: in one run, steps were written in the same second; in one run, hashes were composed by hand and limits counted by hand; in one run, a builder was launched before the person's yes; and in one run, a change was built and never recorded as shipped. So that bookkeeping moved to code, `gdd`, a command in the `engine/` folder that travels with the skills, as decision 42 left room for a script that a trial shows helps. In a first trial with agents, on small cases, each step was logged at its own time, and in one run a finished change got recorded as shipped where, without the layer, it stayed built. So:
    - Every instruction that told an agent to write the log, compute a hash, count limits, time a check or compose a command the layer gives became that command, or went. The orchestrator runs `gdd next` before each step and does the one it names, and when the layer refuses, it does what the refusal says to run instead. The first row of its table sends a change to `gdd-brief`, which ends in `gdd seal` and `gdd brief`: in one run of that trial, the orchestrator skipped loading `gdd-brief` and called `gdd brief` straight from the table.
    - Only the layer writes `gdd/log/`: one line per command, with the clock's time, the hashes git gives and the shape of its event checked, refused when the change's state doesn't allow it. A wrong line is never edited: `gdd correct` adds one that names it.
    - The roles don't call it. They end with their report block as before, and the orchestrator passes it to `gdd report`, which reads the verdict, the color, the findings, the notes, what is left for later and the proofs. `gdd-checks` gives its proofs as a JSON list in a block of its own, and `gdd-review` writes each finding as `f1 <file>:<line> <what>`, the forms the layer reads.
    - `gdd-prepare` leaves the layer in place with the rest, runs `gdd zones` on its draft for pathspecs that match nothing and files no zone covers, and writes the probe and its own step with `gdd step`, as `gdd-harden` writes its own and the exam's. `gdd-harden` takes its counts from `gdd metrics` instead of `grep`. `gdd-brief` takes the floor of a color from `gdd color`, gives the layer the person's request when there's no brief file, so every prompt carries it, and has a brief read once it is sealed, because the layer writes no step before the `brief` one: what the reading changes is a new version.
    - Shipping is the layer's too. `gdd ship <id> --bookkeeping` commits the log, the journals and the backlog on top of the change's branch without touching the orchestrator's copy, and `gdd ship <id> --merge` does that, merges and records the ship for a project that ships by a local merge. A head that differs from what was judged only in that bookkeeping still counts as judged, and after the main branch is merged in, `gdd next` asks for a new review only when the merge touched the change's files. In the walk-through of this version, followed literally, shipping took a commit made by hand, a commit's hash typed in and copies moved aside, until these existed.
    - What the layer can't do is put itself out of an agent's reach: while an agent runs it, it is a file of the repository like any other. CI runs it where no agent writes, as decision 55 says.

    The contract stays `gdd/1`, as decision 54 says.
54. **What the contract gained from the layer.** The layer writes what the contract already had, and a few things more, all optional for a reader:
    - Three events: `answer`, the person's words that close an `ask` that no approval or waiver answers, with the kind of question and the line it answers; `correction`, which names a line and what was wrong with it, and with `void` takes it out of the change's state; and `seal`, the seal moving, from which commit to which and why, so that `<start>` follows it.
    - Fields: `head` in `gates` and in `ship`, the commit judged and the commit shipped; `skipped` in `gates`, each check of the color it didn't run and why; `notes` and `later` in `review`, the reviewer's notes for the builder and what it left for later; `request` in `brief`, the person's words for a change with no brief file.
    - Its journal, `gdd/log/<id>.engine.jsonl`, one line for each time it was called, with the command, its arguments without free text, its exit code, its milliseconds, what it refused and the log line it wrote, which is how the layer's own use is measured and a line written by hand shows.

    The contract stays `gdd/1`: a reader that doesn't know them skips them, and `gdd/limits.sh` counts the same with or without them, except a voided line, which it still counts. The counter stays in the template for now: the layer counts exactly as it does and is tested against it on every sample log.
55. **Version 0.11 needs the layer.** There is no second way of working by hand in the skills: two ways would be two texts to keep true, and the one by hand is the one that failed. In a project the layer is the file `.gdd/gdd`, which the project's `.gitignore` leaves out, or `gdd` on the path. The orchestrator's own skill says where it is, and not the GDD block of `AGENTS.md`, which is at the edge of its hundred words and is read by every agent, the roles that never call the layer included. If it doesn't run, the orchestrator sets it up as `gdd-prepare`'s `references/layer.md` says, and if it can't, it tells the person in one line and stops. What it asks of whoever installs the skills:
    - A Rust toolchain, 1.89 or later, in every copy of the project, because the binary is built there from the plugin's `engine/` with `sh engine/build.sh` and git doesn't keep it. Without one nothing gets built, and the person hears so.
    - CI that runs the layer where no agent writes, applied by the person like the other protections: `gdd verify --all` on every change, and `gdd gates <id> --at .` where the platform builds the change's branch.
    - Another `gdd` on the path is not the layer: in the walk-through of this version, the machine's `gdd` was GNU coreutils' `dd`. The orchestrator looks at `.gdd/gdd` first, and a `gdd` on the path counts only when its `--version` names the layer.

    The contract stays `gdd/1`: a project prepared before 0.11 reads as it did, and gets the layer the first time the orchestrator runs.

56. **A project with no code yet starts with the checks that have something to judge.** In one run of the method benchmark, on an empty project, a shop to build from one sentence, 50 of the 89 minutes of agent time went before the first change could start, and 29 into dead ends. Prepare wrote five checks into the blueprint, the seal, the tests, the lint, the scan for secrets and a browser test. The agent that sets the checks up stopped after 37 seconds, because the product's entry points weren't there; the scan's command was fixed twice after the person's approval, with an approval each time; and the trial of the checks said `stop` with three findings that said the same thing: no source to compile, no tests to run, no screen to drive. Its author decided it as a rule of the method, which follows from gates that start at the minimum and grow. So:
    - In a project with no code, `standing-checks` sets up and tries only `seal` and `secrets`, and CI running them. Every other check stays in the blueprint with its command and a `when` that names what it watches, and asks nothing of a change until there is something for it to reject. The first change that brings what a check watches carries what the check needs: its checks role sets up the runner or the configuration its tests need, sealed with them, and that change's gates run the check for real. The check's trial is an item of its own, `standing-checks-<check id>`, which Prepare leaves right after the first item that brings it work. Nobody is asked to demonstrate a check on code that does not exist, and the three places that read it, `new-project.md`, the checks role and the reviewer of a setup log, say so in those words. A project that already has code sets up and tries all of its standing checks before the first change, as before.
    - The scan for secrets is right the first time. `gdd-prepare`'s reference on gates lists what its command must do: report the file, the line and the kind, never the value; ignore the marks that exempt a line; judge what the change adds from `<start>` to its head; fail when its starting point doesn't exist; and keep its configuration and its ignore file under `gdd/`, where the seal covers them. It gives one command for a scanner in wide use, as an example to adapt, and Prepare tries the command on a planted fake key before it goes in the constitution, so the person approves it once. The template's `secrets` check says what it reports and what breaks it, and names no tool.
    - A cap that runs out on what everything else waits for becomes a question at once. Leaving a change in the backlog and going on is for a change nothing else needs. In that run, setting up the checks used four rounds of three, the orchestrator said for twelve turns that it couldn't raise the limit, and when it finally asked, the person said yes at once. Now, when what stopped is the standing checks or what the next item needs, the orchestrator asks at once for one more round, naming the cap, what was used and what the round buys, and records the yes with `gdd waiver`.
    - Prepare writes a backlog the layer reads. In that run the layer didn't read the first item of the backlog Prepare wrote, because of its headings, and it cost an approval. Prepare adds each item with `gdd backlog add` and sees that `gdd backlog list` reads every one before asking for the approval.

    The contract stays `gdd/1`: a check with a `when` and a `standing-checks-<check id>` item were already in it.
57. **The layer never names the same step again with nothing new, and a fresh copy gets what its checks need.** In one run of the method benchmark, the trial of the checks set up after the first change sent them back. The fix changed the blueprint, so the person approved it, it reached the main branch and the seal took main in. The fix was on the seal, the layer refused the role's report because the seal "didn't move", and it named the same launch again and again: the orchestrator told the person it needed someone who maintains the method, and no later request was built. In another run, the gates' fresh worktree had none of the project's dependencies, its tests ended with "command not found", the layer logged failed gates, and a finished change never shipped. Both times the bookkeeping failed, not the change. So:
    - After a trial that sent a setup's checks back, what the checks role sealed is what the seal holds that the trial didn't judge. A fix sealed before the main branch was merged in, or one that came through main with the person's approval, counts and gets its new trial. In a change, what the seal held unrecorded when `<start>` moved past it counts in the next checks report too.
    - A checks role that stops in a setup log is launched once more. After a second stop the person decides, and every stop after their answer goes to them again. `gdd next` says when a change under way is stopped, and the orchestrator's skill says that nothing under way but the standing checks comes before a request.
    - The blueprint may name `install`, the command that gives a fresh copy what the checks need. The gates run it in their worktree before any check and write what it took. Without it, a check that ends with "command not found" there is the environment: nothing is written, no round is counted, and the layer names `--at`.
    - A role's own runs reach the log. What the builder says each check gave and the commands the reviewer ran come from a `json` block before the report block, as the checks role's proofs do, and the prompt the layer writes asks for it.
    - A change ships its own log, the blueprint's and those of the changes that are over: one still under way ships its log with itself. The minutes of a change stop when it ships. The person's request can come from a file. And one version names the skills, the plugins and the layer, which the check of this repository holds together.

    The contract stays `gdd/1`: `install`, in the blueprint and in a `gates` step, and the `json` block of a builder and of a reviewer are optional.
58. **On a machine nobody set up, the layer says what is missing before it does anything.** Its tests had only run on the computer it was written on, where git knows who its user is. Run on Linux, in a container, two things showed that a CI job meets too:
    - git had no name and email, and a seal, the bookkeeping and a merge all failed at their commit, with git's own long message under a refusal named after something else. Now the layer asks git first, by its own verdict, and stops before it writes a commit or launches a role that will: `next` says so, and the way on is the person's name and email, never ones made up.
    - a checkout another user owns is one git refuses to read. The layer took that for a folder with no git: `verify` checked the logs alone and passed, and the other commands said there was no repository or no main branch. A required check that passes without looking is the one failure CI is there to prevent, so every command now refuses, `verify` included, and names the line that marks the folder as safe. Only `verify --no-git` goes on without git.

    The tests keep git to each repository's own configuration, so none passes because of what the machine has set, and the two that take the right to write away say so and skip where the user writes anyway, as root does.
