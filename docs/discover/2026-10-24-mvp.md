# Discover · 2026-10-24 · MVP

Participants: the human (stakeholder) and the Orchestrator.

## Goal of the first version

Run the Vivarium pilot with `gdd` instead of the Python bootstrap kit (`gdd-kit/` + Spec Kit).

## Decision: MVP = CLI parity + minimal TUI

- **CLI with parity with the bootstrap kit**: set up a project and render the commands for Claude Code, Codex and OpenCode; classify changes; run G2 and G3 with Path Guard; launch the agents through the fixed recipe (Build, G2, G3, Reviewer, merge, pre, G4 pause and resume, promote, observe); Decision Inbox; token log and report. It must pass the same end-to-end cases as the bootstrap kit (t0-t4).
- **Minimal TUI**: the human-facing part that saves the most stops. Exact screens: next Discover topic.

Alternative considered: CLI only, TUI in 0.2 (smaller MVP, reaches Vivarium sooner). The human chose CLI + TUI.

## Kill rule (proposed)

If, on the same kind of change in Vivarium, `gdd` spends more tokens or asks for more human stops than the bootstrap kit, stop and review before adding more TUI. The bootstrap kit keeps working, so nothing is lost.

## TUI screens for the MVP

1. **Setup** (onboarding, `gdd init`; the human's idea): a form for the deterministic part of phase 0. Project name and short description; platform; technology picked from a curated catalog of community-backed stacks (or "not sure"); agents detected on the machine; sensitive areas from a checklist plus free text. A script then writes `gdd/project.toml`, the Brief skeleton, the gate commands from the stack preset and the agent commands, and runs the self-test. If the human is not sure about the technology, or prefers to finish later, the agent skill (`/gdd-setup`) picks up from what the form saved. Same flow without a TTY through flags.
2. **Board**: changes by phase, with color and gate status. Read-only.
3. **Sitting inbox**: scenarios, red zones, red plan and the G4 demo; approve or ask for changes with a key, always through a confirmation that shows exactly what will be recorded.

Later (0.2): live view of a running change, token charts.

## Stack catalog for the MVP

Rust, TypeScript and Python. Each stack is a data sheet (like Spec Kit's per-agent sheets) with:

- the gate commands (lint, types, unit, Gherkin runner, architecture rule, security, licenses, mutation);
- the scenario runner and the minimum skeleton;
- **agent skills for that stack** (the human's idea): how to write steps for its runner, test conventions, how to run its gates. They are rendered for every agent like the GDD commands, and loaded on demand, so the Builder's context stays minimal.

Only community-backed tools (official implementation or the ecosystem's de facto standard), checked by stars and registry downloads.

## Order of the first changes (approved)

1. **Core**: read the configuration; color, lane and gates of a change; log and report (`gdd classify`, `gdd report`).
2. **Gates**: G2 and G3, Path Guard, self-test, creating changes and recording human approvals.
3. **Agents and recipe**: per-agent sheets (Claude Code, Codex, OpenCode), launching them with model and token capture, the fixed recipe with the G4 pause and resume.
4. **What the human sees**: stack catalog and `gdd init`, then the Setup, Board and Sitting inbox screens. Closes with the bootstrap kit's end-to-end cases (t0-t4) passing against `gdd`; then the Vivarium pilot.

Alternative considered: the Board right after the core. Not chosen.

## Learn from core-classify (2026-10-25)

- Recipes cap the memory of test processes during mutation testing (a mutant can turn a loop into endless allocation and take the host down). Linux: `prlimit --as` through the test runner. Open question for the open-source release: the macOS equivalent.
- A library or tool without a screen shows its demo as the readable run of its scenarios.
- The Decision Inbox hides requests resolved before the last launch.
- The Reviewer on red earned its cost: it caught a hard-coded scenario folder that would have sent new scenarios through the fast lane, skipping G1 and G4; neither the scenarios nor mutation testing saw it.

## Learn from guard-and-scope and gate-runner (2026-10-26)

- The Reviewer on red keeps paying for itself: it found four gate-integrity holes that scenarios and mutation testing missed (rules read from the file being guarded, a created-then-deleted protected file, gate commands running before Path Guard, an incomplete scenario selection). Each one also existed in the bootstrap kit, which is the reference: every Reviewer finding in the Rust port is ported back to the kit with an end-to-end case.
- Writing scenarios: hidden examples reuse the visible sentences with new data (G1 enforces it); the Background states everything the behavior depends on (rules table, zone map); changes to protected configuration happen before the build starts.
- A gate failure whose cause is the harness (memory cap, environment) cannot be fixed by the Builder's fix round. In the Rust recipe, the mutation memory cap needs `MALLOC_ARENA_MAX=2`: glibc reserves address space per thread arena, and many test threads hit a 2 GB cap without allocating anything.
- The change's record lives in its merge commit; the working files stay local in `.gdd/`.

## Learn from changes-and-approvals (2026-10-26)

- Split large changes. This one asked one Builder call for 377k output tokens and 50 minutes, and its mutation run (265 mutants) outgrew a fixed step timeout. Rule of thumb for the Orchestrator: when a change ports more than about five commands or its package lists more than about ten paths, propose two changes.
- Hidden examples must not depend on content that a step fabricates (a fixture the visible scenarios never show). Before the sitting, the Orchestrator runs the hidden examples against the reference implementation; the phrasing check in G1 cannot see fixture content.
- A Builder that cannot fix a failure from the code says so in the Decision Inbox instead of loosening the check: it happened here, and it is the behavior the method relies on.
