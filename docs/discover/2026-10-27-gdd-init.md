# Discover · 2026-10-27 · gdd init

Participants: the human (stakeholder) and the Orchestrator. Builds on `2026-10-24-mvp.md` (the
Setup form: name and short description, platform, stack from the catalog or "not sure", agents
found, sensitive areas; same flow with flags and no TTY; `/gdd-setup` finishes what the form left)
and `2026-10-27-stack-sheets.md`.

## 1. Split (decided)

Done at once, `gdd init` would be several times over the size rule and would mix red code (writing
the harness) with yellow code (the form screen), so the strong Builder would write all of it.
Three changes:

1. **init** (red): `gdd init` with flags and no TTY. Writes into `gdd/` the composed stack sheets,
   the protected paths, a first zone map, which agent plays each role, the Brief skeleton,
   `bin/gdd` and CI; installs the agents' commands and runs the self-test. Refuses when the
   project already has GDD.
2. **stack-skeletons** (red, mostly data): the minimum skeleton of a project per stack, and the
   first real run of the TypeScript and Python commands on an empty project.
3. **init-form** (yellow): the form screen on top of the first; the cheaper Builder writes it.

## 2. A folder that already has code (decided, with the human's correction)

`gdd init` accepts an existing repository (and runs `git init` when there is none), and never
overwrites a file: if `bin/gdd`, the CI workflow or `docs/brief.md` already exist, it lists them
and stops before writing anything.

The human corrected the first proposal ("the existing code is not judged backwards"): lint, types
and unit tests check the whole project, so old debt would turn the first change red for reasons
its Builder cannot fix. Decided instead:

1. **Adoption review**: `gdd init` runs every gate command once and records what fails and why, in
   a report.
2. **Proposed refactors**: from that report, Refactor changes, one per area or kind of problem,
   ordered from most to least risk, offered to the human like any change.
3. **Known debt**: the commands that failed in the review run and warn but do not block, until a
   Refactor turns each one green; from then on it blocks again, for good. Mutation and secrets,
   which only look at the change, block from day one.

Later (0.2): each tool's own frozen list of existing errors (ESLint bulk suppressions since 2025,
Ruff `--add-noqa`), so new errors cannot pile up inside a command with known debt either.

## 3. New versions of the files gdd writes (decided)

Two kinds of files:

1. **Owned by gdd** (the agents' commands, the stack instructions, `bin/gdd`): a header says they
   are generated; `gdd agents install` rewrites them and `gdd agents check` names any hand edit.
   As today.
2. **Written once, then the project's** (`gdd/` configuration, the CI workflow, the Brief):
   never overwritten. A later `gdd upgrade` compares what gdd generated then, what it would
   generate now and what the file says today: an untouched file is updated, an edited one gets a
   three-way merge (as git merges branches) and conflicts are left marked for the human. As
   Copier does (3.7k stars, active, 2026-10-27). Since all of it is red harness, `gdd upgrade`
   applies nothing by itself: it opens a change with the proposal, approved at a sitting.

`gdd upgrade` is its own roadmap row. `init` only records, from the start, which gdd version
generated each file, so the upgrade is possible later.

## 4. Only one model family installed (decided)

GDD asks for a Reviewer of another model family than the Builder (they share blind spots: Codex
caught holes Opus did not see). With one family only, every yellow or red change would be refused
and the tool would be useless to many people. Decided: `gdd init` works anyway, in the open.

- The Setup says so ("one family only: the Reviewer will be of the same kind as the Builder") and
  suggests a second one (OpenCode takes models from many providers).
- Going on records the acceptance in the configuration, with its date (without a screen, a flag
  says it; without it, `init` refuses and explains).
- Every G4 and every merge commit say "Reviewer of the same family (accepted at the Setup)".
- When a second family appears, `gdd status` says so, to change the Reviewer.

Alternative not chosen: always require two families: safer, but it leaves out whoever has one
subscription only.

## Learn while preparing init (Orchestrator)

The adoption review, the proposed Refactor changes and the known debt change how gates treat a
failing command: with them `init` would be far over the size rule. They go to their own change,
**init-adopt**, after init; init already accepts a repository with code and never overwrites.

## 5. First real run of the stack sheets (Orchestrator, before stack-skeletons)

A minimal skeleton per stack (a library function, two unit tests, the scenario runner wired to
`GDD_FEATURES`/`GDD_HIDDEN`) and every gate command of its sheet, run for real on 2026-10-27
(Node 22, Python 3.13 with uv 0.12, Rust 1.9x; OSV-Scanner 2.7.0). Each runner was also checked
with one real scenario, a hidden one, a missing step (must fail) and a surviving mutant (must
fail).

What the paper check had missed:

- **Rust**: `clippy --all-targets` skips a test target with `test = false`, so the lint never saw
  the scenario steps: lint needs `--test acceptance` too. The project's own crate needs
  `[licenses.private] ignore = true` in `deny.toml` (publish = false), or cargo-deny fails on it.
- **TypeScript**: ESLint needs CommonJS globals for `*.cjs` config files; dependency-cruiser's
  `no-orphans` rule fails a one-file project (dropped). A fresh install of StrykerJS brings a
  vulnerable transitive `qs` (dev only): G3 security is red on day one. Licenses: several dev
  tools are CC-BY-4.0, BlueOak-1.0.0 or CC0-1.0; an `osv-scanner.toml` that ignores licenses in
  the dev group (vulnerabilities still scanned) makes the check about what ships.
- **Python**: bare `ruff`/`pytest` need an activated environment and pip has no lock file; with
  uv every command is `uv run ...`, `uv sync --locked` installs and `uv lock --check` is the
  lockfile check. pytest exits 5 when no scenario exists yet. OSV-Scanner does not see uv's dev
  group and reads several PyPI licenses as non-standard: licenses are checked on the runtime
  requirements (`uv export --no-dev`). mutmut 3.8 renamed its settings (`source_paths`,
  `pytest_add_cli_args_test_selection`).
- **Self-test**: check 1 ("a failing test turns G2 red") also passes when G2 was already red
  without the planted test (for example, a tool missing): it must first see G2 green.

All three stacks end green with the fixes, and red on a survivor or a missing step.

## 6. Python with uv (decided)

The Python sheet moves from pip to uv (91k stars, by Astral): `uv sync --locked` installs, every
command runs with `uv run`, and `uv lock --check` is the lockfile check Python lacked. Checked for
real on the skeleton.

## 7. Vulnerabilities in dev tools block, with exceptions (decided)

They block, dev tools included: they run on the developer's machine and in CI, next to the keys
(the npm worms of 2025 spread through dev dependencies). The human added: the developer may
configure exceptions, under their own responsibility. Licenses are only checked on what ships.

How (Orchestrator): each exception lives in the scanner's own file, which already supports them
with a reason: `osv-scanner.toml` (`[[IgnoredVulns]]` id, reason, `ignoreUntil`) for TypeScript and
Python, `deny.toml` (`[advisories] ignore`, id and reason) for Rust. Those files are supply chain,
so a red zone: adding an exception is a red change, approved at a sitting, and the merge commit
keeps who and when. gdd shows the active exceptions in `gdd status` and at G4, and refuses one
without a reason. A red on day one goes through the same path (known debt and a proposed Refactor
once init-adopt exists).

## init-adopt: shape (Orchestrator, 2026-10-27)

- The adoption review is its own command, `gdd adopt`, not part of `gdd init`: init is offline
  and the gate commands cannot run before `gdd bootstrap` installs the dependencies.
- Known debt lives in `gdd/debt.toml` (protected, red): written once by `gdd adopt`, and only
  shrunk by the merge of a change whose G2/G3 saw the command pass ("Known debt paid" in the merge
  commit). No one else writes it, so a real failure cannot be turned into a warning by a Builder.
- One proposed Refactor per failing command (kind of problem), riskiest first: security,
  dependencies, types, unit, architecture, quality, lint, lockfile. Per-area Refactors need each
  tool's output parsed: later.
- Learn running the duplicate and unused-code tools moves to its own small Change
  (`learn-tools`) to keep init-adopt at one module family.
