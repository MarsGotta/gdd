Your agent says "done." The gate checks if it's true.

Gate-Driven Development (GDD) is a way to build quality products with AI agents without supervising them step by step. Before the agent starts, you decide what has to be true. To get through, it has to prove it before something it cannot touch.

Agents write fast and almost right.

It isn't just you. In Stack Overflow's 2025 survey, 66% of developers named AI solutions that are "almost right, but not quite" as their biggest frustration. Stack Overflow, 2025

You don't persuade an agent with words. You put gates on it.

A gate is what has to be proven before going on.

We don't develop code, or even tests. We write what must be true and design the gates our agents go through.
  1. 1

    Before it starts, you decide what has to be true.

    That a charge happens only once. That a total is never negative. You write it yourself, before the agent touches anything.

  2. 2

    It's proven by something the agent can't touch.

    A test, a linter or another person's review: things you already use, which don't depend on what the agent says.

  3. 3

    More risk, more checks.

    If the change is a typo, you barely notice. If it touches payment, you ask for more, and it may call you.

  4. 4

    What slips through gets hardened.

    You add the check that would have stopped it. It won't get in that way again. One that no longer adds anything, you relax or retire.

Risk decides, not the size of the change.

Choose what you ask the agent and see which gates stand in front of it, and how many times it calls you.

GDD puts order into what already works.

Controls outside the agent, demands that follow the risk, and a person where it matters. GDD gives that a common language, a test to know whether a gate holds, and a path to follow.

How it differs from vibe coding, SDD and TDD.

Vibe coding, specifications and TDD answer how to build. GDD answers another question: what has to be proven before a change is done.

One rule, seven principles, five moments.

All of GDD fits on one page. These are the five moments the work goes through, from the first day until something slips through.

  1. Prepare

    You write the blueprint and build the first gates. You try to fool them on purpose, and the rest come when a change needs them.

  2. Brief

    Rules, a few scenarios and a first estimate of the risk.

  3. Execute

    The agent gets through the gates one by one. If it gets stuck, it stops and asks.

  4. Close

    With the change in use, a person checks whether it helped.

  5. Harden

    What slipped through becomes a check, and what no longer adds anything is relaxed or retired. The blueprint changes and you go back to Prepare.

The seven principles

  1. 1Gates come first, and nobody skips them, not even you.
  2. 2A gate that never closes is not a gate.
  3. 3To each gate, its context.
  4. 4You get through a gate with facts, not words.
  5. 5Whoever goes through the gate doesn't decide how it's validated.
  6. 6More risk, more checks, and your approval only where it matters.
  7. 7Gates with cracks get hardened.

A gate holds if you answer yes four times

  • Was it decided before the agent started?
  • Is it checked without trusting what the agent says?
  • Is it out of the agent's reach, so that touching it does the agent no good?
  • Have you seen it reject something done wrong, real or planted on purpose?
