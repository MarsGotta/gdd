The whole path

The delicate case had one gate and your approval. My whole path, the one I use in my projects, has five gates and picks up with the same discount codes. You don't need all of this to start: it's as far as you can take it, and what T-minus, the engine I'm building, will automate. The stumbles, in italics, are made up, so you can see what happens when something goes wrong. If a word doesn't ring a bell, it's in The pieces and the roles.

The five gates are the preparation, which the team approves once per project, and four on every change: at the scenarios and at the release a person decides, and at the loop and the PR, machines. The arrows on the left are the trips back when something fails.

First, the preparation, once per project. I create the blueprint, the agent's environment (everything around it: tools, permissions and checks) and the gates, and the team approves it. I add the skills for the technologies I'm going to use, the linters and the deterministic tools that will help me in the production process. If there are ready-made rules for my area, I start from them, because they bring almost all of that. In the store, I mark payments as a delicate zone and the agents work without access to production.

  1. I define what has to happen. I start by talking with the orchestrator: I tell it what I want and it helps me pin it down, push back on it or find a better solution. With that it writes the feature's scenarios in Gherkin. I read them and approve or reject them, and once they're approved, a large share of the use cases can already be automated. If it comes out too big, it proposes a series of smaller changes, and I decide. Here I reject the first version: an expired code is missing.
  2. I brief the checks. An agent writes the tests for those features, e2e ones too (the ones that run through the whole application, the way a user would). CI checks that they fail, and for the right reason. A reviewer checks that they cover the scenarios I approved and tries a wrong solution on them on purpose. If return 45 opened the gate, the checks would go back to whoever made them.
  3. I brief another agent on the code. A different agent writes the code that makes those tests pass and runs it through several linters, which warn it about quality and security problems. It repeats that loop until a reviewer with a clean context runs the change and only passes it if it works. Here comes the first rejection: the discount is duplicated in the cart and in the checkout.
  4. If the agent thinks a test is wrong, it tells me. It doesn't touch it: it stops and says so. The check gets fixed by whoever made it or by a person, never by whoever is getting through the gate. Here, three items at €9.95 with 10% off come to €26.87 on the total and €26.88 when rounding per line. The test expects the first and the cart does the second. It isn't an agent error: it's a decision nobody had made, and I make it.
  5. If it gets stuck, it stops. That loop can only repeat twice. On the third, the orchestrator decides whether the scope or the approach has to change, and talks it over with me.
  6. I let it reach the PR, but I don't merge anything yet. When the reviewer passes it, the agent pushes the PR. The e2e tests run there and another reviewer looks at the whole thing, and if something has to change, the branch goes back to the agent. Here an e2e test fails: the order summary still shows the price without the discount.
  7. I look where it matters. If all goes well and the change touches red zones, as it does here, I review the code and check how it would be undone.
  8. I give the last approval. The change is deployed from its branch to staging, or behind a feature flag (the feature stays off until someone turns it on), depending on the project. If it touches red zones, I wait until I've reviewed it; if not, it deploys on its own. There I check that it works and approve. Only then does CI check everything again and, if it passes, the change is merged and ships. If I say no, I close the PR, and there's nothing to undo on the main branch. GDD doesn't require this approval: it's a person's check I've chosen in my projects, and for anything delicate I recommend it.
  9. I harden what failed. With that approval, the orchestrator analyzes what failed along the way and the cracks it saw, and proposes what to harden. Here it proposes an architecture rule: the discount is only calculated in one place. If a negative discount had slipped through, that case would become a new test and a question on the reviewer's exam. And if what happened touches the agent's environment, I go over the blueprint and propose the tweak, and the team approves it: an agent never decides that.

When the path goes sideways

If this happensWhat happens
The change is the text on a buttonIt's green: the same gates, at a different difficulty. The standard checks pass and I, to start with, don't review the code.
There is an emergency in productionThe first thing I try is to undo it. If a fix is needed, a person approves it through the emergency gate, it gets recorded, and afterward it goes through the normal gates.
Almost everything comes out redThe engine's report warns you: the blueprint is wrong, you've marked too much as delicate.
When approving, you ask for a tweakIt goes back to the agent with your words. Since it changes what you saw, the gates and your approval are requested again.
There's a question to answer before buildingI treat it as a spike, an exploration with fewer gates: its code stays on its branch and only the decision comes through.

So far I've assumed the agent plays fair. What happens when it doesn't is in How a gate gets fooled.
