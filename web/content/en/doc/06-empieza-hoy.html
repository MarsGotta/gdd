Start today

GDD has its own vocabulary, but underneath it's things you already know. You don't need any new tool to start: if you've ever made CI mandatory, you've already put up a gate. And you don't have to be Stripe or have a platform team either.

Every word, with what you already have

Some of these options depend on your platform and your plan, and the details come with the first gate, a bit further down.

What if I can't be bothered to specify every change? If the change is green, you specify nothing. If it isn't, you don't write a specification: you read a few scenarios an agent drafts. The standing checks get set up once and then work on their own. And if a change still feels like a chore, something is extra: take that gate out, with your team's approval, instead of skipping it.

And when do I add more? When something asks for it. Is something slipping through that the tests can't see? Add a reviewer. Does the same failure keep coming back? A standing check. Is splitting up the work eating your time? An orchestrator. Do you want to meet the whole core without keeping count by hand? An engine. Every gate costs tokens, waiting and maintenance, so each one has to earn its place.

And in what order? Start with a gate that really closes, like the one a little further down. Once it has spent a while catching what it should, start letting go: stop looking yourself at the changes where you never find anything anymore, beginning with the ones with the least risk. Several agents at once come last, because with a gate that doesn't close yet, all you get is more slipping through, and faster.

And how do I know it pays off? Write down three things from day one, even by hand: how many times each change gets stopped, how long it takes to ship and what slips through. Before you start, look in your history at what that looked like without GDD, because without that baseline all you'll have is an impression. An engine records it for you, but the question is the same.

To start: your first gate

The shop in Hands on has four gates, but one is enough to start. It's the fourth of the six steps of a change, the gate that closes. On GitHub you need this, and on other platforms the names change, but the idea is the same.

In CI go the two checks that act as the gate, and for them you work with two branches:

  • checks/<change>: the approved tests, and only you write to it. It's the seal of the change: what keeps the checks out of the agent's reach.
  • <change>: the agent's branch, which comes off the one above. It can add tests, but it can't change or delete the approved ones, or touch what decides how they run, like package.json or CI itself. If it needs to, it stops and asks you, and you make the change on the checks branch.

The first one, seal, compares the two. If there's no checks branch, it only lets through what you've marked as green in the file. If a change doesn't need new tests, create its checks/<change> branch from main.

It lives in a file of its own because it uses pull_request_target, and with it GitHub always runs the version on main, even if the agent changes or deletes it on its branch. Since it runs with the repository's permissions, don't put anything there that installs or runs what the agent brings. That's the job of the second one, gate, which runs the tests:

In a CODEOWNERS goes whatever is delicate, CI itself included. If the agent could change those checks, the gate would be worthless.

In the repository settings go two rules:

  • On the main branch: require a PR, passing the seal and gate checks, and review by the code owners when their paths are touched. Tie both to GitHub Actions, because otherwise anyone with write permission can mark them as passed. Dismiss approvals when a new push comes in: your approval only covers what you saw. Not even whoever administers the repository gets to skip it.
  • On checks/**/*: only you can create and write, with a ruleset. That way the agent can't change what you approved or make up a check. With checks/*, branches with a slash in their name would be left out, and the agent picks the name of its own.

Watch your credentials. This only works if the agent uses its own, from another account or an app: with yours it can do whatever you can, and a token of yours with fewer permissions is still you. A PR you open yourself that touches your paths can be merged without anyone approving it. Give them permission to write code and open PRs, but not to touch workflows, because one it pushes gets run even if its PR never merges, and it can use the repository's secrets. If your agent allows it, also forbid it from editing tests/, which saves you rounds, although the gate is still CI.

It depends on your plan. On GitHub, protected branches and rulesets are free on public repositories and paid on private ones. Without them, CI warns but doesn't block: it's a gate in the rule degree, which holds for as long as you look. On GitLab, protected branches are on the free plan and Code Owners on Premium: without it, let only people with the maintainer role merge.

When main changes. If another change touches an approved test or package.json, bring that change into the checks branch, or the gate will close on you.

What this gate doesn't cover. It's a real gate, but it doesn't cover the whole core (what's missing is in The engine), and it won't catch a solution tailored to the tests either: that's what the reviewer and the hidden examples are for.
