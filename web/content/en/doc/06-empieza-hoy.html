A gate by hand

This is the path without the skills: you put up a gate yourself, with what your platform already has. If you'd rather have your agents carry the method for you, go to Get started.

GDD has its own vocabulary, but underneath it's things you already know. You don't need any new tool to start: if you've ever made CI mandatory, you've already put up a gate. And you don't have to be Stripe or have a platform team either.

To start: your first gate

The shop in Hands on has four gates, but one is enough to start. It's the fourth of the seven steps of a change, the gate that closes.

The steps are for GitHub. On other platforms the names change, but the idea is the same: two checks in CI, seal and gate, and two branches per change.

1. Create the checks branch. It's called checks/<change> and holds the approved tests, which another agent can draft. Only you write to that branch. It's the seal of the change: what keeps the checks out of the agent's reach.

If a change doesn't need new tests, create its checks/<change> branch anyway, from main.

2. Create the agent's branch. It's called <change> and comes off the one above. The agent can add tests, but it can't change or delete the approved ones, or touch what decides how they run, like package.json or CI itself.

If it needs to, it stops and asks you, and you make the change on the checks branch.

3. Add the seal check. It's called seal and compares the two branches. If there's no checks branch, it only lets through what you've marked as green in the file.

It lives in a file of its own because it uses pull_request_target, and with it GitHub always runs the version on main, even if the agent changes or deletes it on its branch.

Since it runs with the repository's permissions, don't put anything there that installs or runs what the agent brings. That's the job of the second check.

4. Add the check for the tests. It's called gate and it's the one that runs the tests:

5. Give whatever is delicate an owner, CI itself included. It goes in a CODEOWNERS. If the agent could change those checks, the gate would be worthless.

6. Protect the main branch. In the repository settings, require a PR, passing the seal and gate checks, and review by the code owners when their paths are touched.

Tie both checks to GitHub Actions, because otherwise anyone with write permission can mark them as passed.

Dismiss approvals when a new push comes in: your approval only covers what you saw. And make sure not even whoever administers the repository gets to skip this rule.

7. Reserve the checks branch. With a ruleset on checks/**/*, so that only you can create and write. That way the agent can't change what you approved or make up a check.

With checks/*, branches with a slash in their name would be left out, and the agent picks the name of its own.

8. Give the agent its own credentials. From another account or an app. With yours it can do whatever you can, and a token of yours with fewer permissions is still you. A PR you open yourself that touches your paths can be merged without anyone approving it.

Give it permission to write code and open PRs, but not to touch workflows, because one it pushes gets run even if its PR never merges, and it can use the repository's secrets.

If your agent allows it, also forbid it from editing tests/. That saves you rounds, although the gate is still CI.

And that's it. With this, an agent's change doesn't get into main without passing the tests you approved, exactly as you approved them. Whether that truly blocks it, and doesn't just warn, depends on your plan.

What it guarantees, and what it doesn't

On GitHub, protected branches and rulesets are free on public repositories and paid on private ones. Without them, CI warns but doesn't block: it's a gate in the rule degree, which holds for as long as you look.

On GitLab, protected branches are on the free plan and Code Owners on Premium: without it, let only people with the maintainer role merge.

With protected branches and the ruleset on, it's a real gate, although it doesn't cover everything:

It guaranteesIt doesn't guarantee
That the approved tests don't change or disappear.That they're enough: it won't catch a solution tailored to the tests. That's what the reviewer and the hidden examples are for.
That nothing gets merged with a failing test.The whole core: what's missing is in The engine.
That the agent doesn't change what you approved, if it uses its own credentials.Anything, if it uses yours: with them it can do whatever you can.
That nobody skips the review of the delicate paths, not even whoever administers the repository.That whoever administers doesn't change the settings: they can take the protection off whenever they want.

Later on

When main changes. If another change touches an approved test or package.json, bring that change into the checks branch, or the gate will close on you.

If you install the skills later. The skills seal each change on another branch, gdd-seal/<id>, and check the seal with their layer, not with seal. Before you switch, take seal out of the required checks, or their pull requests will get stuck. Your agent gives you what the layer puts in its place when it sets up.

Four questions

What if I can't be bothered to specify every change?

If the change is green, you specify nothing. If it isn't, you don't write a specification: you read the rules and a few scenarios an agent drafts. The standing checks get set up once and then work on their own.

And if a change still feels like a chore, something is extra: take that gate out, with your approval or your team's, instead of skipping it.

And when do I add more?

When something asks for it. Is something slipping through that the tests can't see? Add a reviewer. Does the same failure keep coming back? A standing check. Is splitting up the work eating your time? An orchestrator. Do you want to meet the whole core without keeping count by hand? An engine.

Every gate costs tokens, waiting and maintenance, so each one has to earn its place.

And in what order?

Start with a gate that really closes, like the one in this chapter. Once it has spent a while catching what it should, start letting go: stop looking yourself at the changes where you never find anything anymore, beginning with the ones with the least risk.

Several agents at once come last, because with a gate that doesn't close yet, all you get is more slipping through, and faster.

And how do I know it pays off?

Write down three things from day one, even by hand: how many times each change gets stopped, how long it takes to ship and what slips through.

Before you start, look in your history at what that looked like without GDD, because without that baseline all you'll have is an impression. An engine records it for you, but the question is the same.
