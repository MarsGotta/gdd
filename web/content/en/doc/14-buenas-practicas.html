Good practices

This is more of a menu than a rulebook: your team picks what works for it, and the only thing that isn't negotiable is in The core. There's just one rule that holds for all of them: loosening a gate is always approved by the team.

Each practice stands on its own, so you can jump in anywhere. Next to the title I tell you which principle it protects and whether it's only for software or for an engine like T-minus. The ones marked "core" are already part of The core, and here I explain how to make them visible in your project.

Your first gate, ready to copy, is in Start today.

Prepare

1. Mark as delicate whatever is expensive if it fails. principle 6 In software, I'd start with payments, access and permissions, deployments and CI, the updater, customer data and the blueprint itself. Mark behaviors too, because if a change in promos/ alters what gets charged, it's Red even if it doesn't touch payments/. A machine only sees paths, so that's the minimum it marks; an agent or a detector can raise the risk, but never lower it. And zones go stale over time: a model can propose changes, but the team approves them.

2. Start with few gates, but strict ones. principle 7 Few, because each one costs something, and you'll add another when something slips through. And strict: before marking more things Red, add checks to the gates you already have. When it's time to loosen, do it with the data in front of you (stops, waiting, what slips through). If you have ready-made rules, start from them.

3. Write each gate as a scenario. principle 2 "The code stays clean" sounds good and commits you to nothing. If you have to write it with its Given, its When and its Then, you have to spell out what it means, and if you can't get to the Then, it isn't a gate yet. An agent can draft it for you: you read it and correct it.

What teaches you most about a gate is what it rejects, so I'd start there:

Written like this, you're already answering the fourth question in the Manifesto, the one about watching it reject something badly done, and if you run it, you have the proof. But the text alone checks nothing: whatever runs each step is a check too, so the agent doesn't touch it, and a step with nothing behind it has to fail. Keep it to a few lines, because I don't want this turning into another long specification. And don't wrap every tool in a scenario: "Then the linter reports no errors" tells nobody anything.

4. Ask for more checks the higher the risk. principle 6 The examples for each level are my proposal, inspired by Anthropic.

  • Green (low): documentation, text, internal functions or additive changes behind a flag. Machines are enough.
  • Yellow (medium): ordinary product changes. Machines and a reviewer, and a person if you decide so.
  • Red (high): whatever you marked as delicate. A person too.
  • The most delicate (within Red): two people, if the team turns it on and the change is big. It comes switched off because some projects are run by a single person.

5. Confine the agent before opening its first gate. core The gates look at what ships, so first limit what the agent can break while it works. In software, that means an isolated environment, with no access to production, with its own credentials, a restricted network and rules for dangerous commands. OpenAI uses a sandbox with a restricted network, and Spotify, containers with limited permissions.

6. Hold back the bloat too. principle 4 Tests don't notice when three features take up hundreds of thousands of lines. In software, set a size cap per change, and have a machine check complexity, duplication and architecture. Each blueprint sets the cap in the unit of its area (in a contract, clauses). Generated code is excluded only if its paths are declared and regenerating it gives the same result.

7. Adopt GDD by zones. principle 1 If you have legacy code without tests, start with the part you're about to touch, with tests that pin down how it behaves today, and expand from there. What already fails is recorded as debt: it warns, doesn't stop, and can't get worse. Recording it is loosening, so the team approves it.

Böckeler warns about this: the agent's environment is needed most exactly where it's hardest to build. Stripe could lean on more than three million tests; if you don't have them, that's your first job.

8. Keep the constitution and the cross-cutting context simple and clear. principle 3 They go along on every call, so every extra line gets paid for at every gate. Write what the agent can't work out from the code, in sentences it can actually follow, and if something only matters at one gate, move it to that gate. If you're not sure a rule is needed, take it out and see whether the gates notice. The agent reads them but doesn't touch them.

Brief

9. Give the agent short instructions, with its gates. principle 4 That way it knows what it has to prove, not just what it has to do. In software, a short AGENTS.md is enough, with the checks it has to pass and links to more documents. Ready-made rules can bring skills, but those advise, they don't check.

10. Small changes: if it doesn't fit, split it. principle 6 A small change is easier to review, debug and undo. If it doesn't fit, the orchestrator proposes a series of changes and the author approves it in one go. So that it doesn't depend on the model's goodwill, there's a size cap, which measures what was actually touched, and going over it is a person's call, for that change only, and it goes on record.

Splitting doesn't lower the risk: each part has the level of what it touches. If your project asks for a person to approve Red, each Red part needs its own, because an approval is only worth what was seen.

Each part has to leave the product working and be able to be undone on its own. If it doesn't deliver anything yet, it goes behind a switch, and turning it on is another change, at the level of what it turns on. Google asks for small, self-contained changes, and lets you reject one just for being too big.

11. Test the checks before you trust them. principle 2 Feed them wrong solutions or mutants: if they let them through, they're hollow (why they have to fail for the right reason is in The seven principles). Write more than one case, as when triangulating in TDD, so that a custom-made solution isn't enough. And if you can, don't have the model that will do the work write them.

12. For delicate changes, keep examples the agent can't see. principle 5 By default, I'd leave the tests visible but read-only: in ImpossibleBench, hiding them almost eliminated cheating but made legitimate work worse, and read-only kept it. On Red, add a hidden set too, like the scenarios at StrongDM.

Execute

13. Run the cheap stuff while working. principle 4, software Set up formatters and linters with hooks that fire on their own, before reaching the gate. The gate checks it again, because the hook saves rounds but doesn't replace it.

14. The reviewer tests with a clean context. principle 5 It doesn't see the agent's conversation, only the change, the blueprint and the checks, and it's better if it comes from a different provider. In software, before the PR, a /code-review or a fresh subagent will do. That it runs the change is covered in The pieces and the roles.

15. Give the reviewer the failures that keep repeating. principle 7 What repeats becomes a check first, and only if a machine can't check it does it go to the reviewer. In software, write it down in a short REVIEW.md: what counts as a failure here (in docs, for example, that it lies), which paths to ignore, how many minor nitpicks at most, and that every finding carries a file and a line. Its instructions are always read from the main branch, never from the change itself.

16. Set a limit on rounds, and after that only what's new. principle 4 By default, two fix rounds per gate, and the team adjusts it. The change also has an overall cap on rounds, time and cost, and loops since the PR or since the last approval count too. If it doesn't converge, the approach has to be rethought, and whoever handles that stop is the author.

After the first round, the reviewer only retests what changed. It points out the whole class of failure, doesn't repeat findings, and marks as "was already there" whatever the change didn't introduce.

17. An unstable gate doesn't burn attempts. principle 4, software If a test fails and it has nothing to do with the change, rerun it (with a cap, and only if it also fails without the change) and raise a warning, because sometimes it's the code itself that makes it fail now and then. Putting it in quarantine is the team's decision, and the agent never disables it: Spotify saw agents that disabled unstable tests.

When a person approves

18. What arrives for approval answers four questions. principle 6 How was it tested? What risk does it carry? How is it undone? And what can't the gates see? If you don't know what would slip past them, ask for a real review, not a quick approval. In software, the PR template carries the first three (Tested, Risk, How to undo), and whatever explains how it works is marked as an agent's text.

19. An agent never approves in place of a person. core In software, protect the branches and put CODEOWNERS on payments, access and deployments. GitHub is along the same lines: its cloud agent can't approve or merge a PR.

If your industry requires a reviewer different from the author, like PCI DSS, treat whoever directed the agent as the author: the standard doesn't address that case, and it's the most prudent reading. And if you work alone, you're author and team at once. Make it visible, with a deadline and a substitute, and watch how long each approval lasts, because approving in seconds is approving blind.

20. Understand the part you're about to touch, not every line. principle 6 Ask for an explanation of that part of the code instead of reading trivial changes line by line.

21. Define the emergency gate before you need it. principle 1 Decide ahead of time who can open it, for what and what happens afterward. In an emergency, the first thing is to undo the change. If a fix is needed, it passes the quick checks, a person approves it, it gets recorded and then it goes through the normal gates. Put a deadline on it: while it's pending, no new change starts in that zone.

Harden

22. Ship with a way back and watch what happens afterward. principle 7, software Use feature flags, gradual rollout and a tested rollback, because some errors will pass every gate. At Spotify, an automatic update slipped through, passed the checks and failed in production, and Anthropic counts on undoing most errors within minutes.

23. Write down everything that slips through and which layer should have caught it. principle 7 Record each thing that slips through (if you're unsure what counts, it's in The seven principles) with the change that introduced it and what fixed it, and ask someone who knows that part to confirm the failure is real and where it was.

Then look at which gate should have caught it and what it was missing. If a machine can check it, make it a check; if not, it goes into the reviewer's instructions. Either way, it ends up in its exam (practice 24).

24. What slips through is the reviewer's exam. principle 7 Every failure that slips through and is confirmed is a case in the exam, and while you have no real cases, start with failures planted on purpose. If you change the reviewer's model, instructions or tools, run all the cases through it again: if its score drops, the change doesn't stay, because catching real failures counts for more than saving rounds. Anthropic, in addition, runs it every day.

25. Measure the reviewer's noise. principle 7 Record what happens with each finding (fixed, false, intended or unimportant) and run it on clean changes too, to count how many times it would have pushed someone to make a harmful change. Noise costs more when the one fixing is an agent: it doesn't dismiss a minor nitpick, it fixes it, and that opens another round.

26. Now and then, review what you already accepted. principle 7 Have a reviewer read the code that's already been accepted. That's how the holes show up that no new change would have revealed, like a test configuration that stayed active in production.

27. Review the gates too, and retire the ones you don't need. principle 7 Every failure adds a gate, and if you never remove any, it all piles up and the cost only goes up. Now and then, look at what each one catches, carefully: as Böckeler points out, a gate that never fires can mean quality or that it detects nothing, so check that it still closes before deciding. Retiring it changes the blueprint, and you approve that, or your team does.

So that it doesn't rest on an impression, write in the blueprint the figure that would make you remove one, as something you can count. It can be how many changes it has gone without catching anything real, or what it costs you on each one. The same goes for the reviewer's questions, which pile up just the same. And a new model is no reason to remove a check, because a check judges your product and not the model. What can change is how much model each level of risk needs: if changes get through in fewer rounds with the new one, try a lighter one on green, or lower the limits.

28. Let the engine harden on its own, with approved thresholds. principle 7, engine This is an idea to test: if what slips through goes over a threshold, the engine raises the level on its own. A person approves the thresholds beforehand, and loosening is still up to a person. The core doesn't allow it today (changing the blueprint always takes approval), and Anthropic admits it doesn't have anything like it yet.

29. Look at the report on your blueprint every so often. principle 7, engine It tells you four things.

  • Per gate: how many times it fires, how many of those were a real failure, what slipped past it and what it costs. If it always fires for the same thing, it can be caught earlier.
  • Per zone: if the risk goes up often, it's badly marked; if almost everything comes out Red, you're marking too much.
  • Per approval: if it lasts seconds, that's approving blind (practice 19); if many touch-ups are requested, what matters to you isn't in the checks.
  • Per round: if the agent gives up or disputes the same thing every time, or the reviewer takes a long time to sign off, the brief or the checks are wrong.

The report warns and proposes, but changes nothing: touching the blueprint still needs the team.

30. Compare against a baseline, not your impression. principle 7 Before adopting GDD, save how you work (how long a change takes to ship, how many fail, how much rework there is) using the definitions from DORA. Then compare the same project with itself, and be upfront about how many changes you measured it with: DORA itself warns that comparing very different systems misleads. The rest is in How it is measured.

If you come from TDD, you're probably wondering what changes compared to what you already do. That's what What about TDD? is about.
