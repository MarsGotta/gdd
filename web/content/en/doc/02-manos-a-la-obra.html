Hands on

You know the idea by now, so let's put it to work. This part is guided, so don't worry: I'll go piece by piece and explain each thing just when you need it.

We've been asked to build an online shop. I think it's an example we all know, and it holds the whole range of risk. A text that goes wrong is irrelevant. A payment gateway that goes wrong charges your customers twice. First we'll prepare the gates together, and then we'll review four changes to see whether what we've prepared holds up. The shop and everything that happens to it are made up.

Prepare: before you write a line

The first thing is to plan which gates are needed and build them. No code yet, because the gates come first.

For this step I recommend leaning on a GDD engine, the program that enforces the method, because it takes a lot of what you're about to see off your plate. Mine, T-minus, is still in development, so here we'll use only what you already have at hand day to day: a repository, CI and an agent.

Before you start planning the agent's environment, I recommend asking yourself these questions. Next to each one is what we'd answer for the shop.

QuestionIn the shop
What's it about?A catalog, a cart, a payment and the customers' accounts
What would be serious if it goes wrong?Charging twice, or someone getting into the admin panel
What can a machine check, and what does someone have to look at?The total of an order is checked by a test. Whether the payment makes sense, someone looks at
What does it mean to ship?That it works in production, not that the agent says so
Can it be undone?A text, yes. A charge that's been made or a migration that deletes data, no

Gates, like features, evolve over time, and that's part of the magic of GDD. For now, and to keep the example simple, we'll focus on small, concrete cases.

What the agent always carries

Before the gates, there are things the agent is going to need at all of them: what the shop is about, how we work and what's not up for negotiation. That's the constitution, a short document with the project's rules. In ours we'd write, for example, that prices are stored in cents and that card details are never stored.

Alongside it go the tools and skills used throughout the flow, like the ones for the shop's technologies. All of that is the cross-cutting context, and the agent always carries it, at every gate. Since it goes along on every call, the simpler and clearer the better: if something only matters at one gate, it stays at that gate. An engine helps you draft it, and it's something T-minus will do during Prepare.

The four gates

A gate is what the agent has to prove before moving on. For this shop we'll put four, one after another: scenario, testing, refactoring and reviewing. In your project they can be others, and what stays the same are the six steps of a change.

Each gate carries two things. Its checks are what shows it has really been passed: a test, a linter, another agent or a person. Its context is what we give the agent, on top of what it always carries, so it can get through, and it's what usually gets forgotten. A gate without context is a wall: the agent guesses, fails, guesses again, and you pay for every round. That's why each gate gets what it needs for that gate, and nothing more: the agent always starts with a clean context. That does include what the previous gate generated, like the scenarios, but not its conversation.

GateWhat it has to proveContextChecks, at most
ScenarioThat we know what has to passThe request and the design in FigmaThe scenarios are well written, and you read them if needed
TestingThat it does what the scenarios sayThe scenarios, the schemas and the data modelTests created by another model
RefactoringThat the code can be maintainedGood-practice skillsLinters, Sonar and typing, and a reviewer from another model
ReviewingThat it's ready to go inThe PRCI and a code reviewer: another reviewer, a person or both

Scenario. Before building anything, we write down what has to pass. We do it in Gherkin, a language made to describe behavior with Given, When and Then sentences. Anyone can read it, and a tool like Cucumber can run it. You give an agent the request and the design in Figma, and it writes it for you:

Testing. This check is shaped to each change, which is why I call it custom. Another model turns the scenarios into tests, and those are the tests our agent will have to pass. There's a reason someone else writes them: whoever goes through the gate doesn't decide how it's validated. Before moving on they have to fail, and for the right reason, because a gate that never closes isn't a gate. We give the agent the scenarios, plus the schemas and the data model, so it doesn't make up the shape of an order.

Refactoring. With the tests passing, we ask it to improve the code, because working and being maintainable are different things. The checks on this gate are standard, because they apply to the whole project, and deterministic, because the same code always gives the same result: linters, typing and Sonar, a quality analyzer. For context we give it good-practice skills. And when there's risk, it also carries a reviewer: another agent, from another model and with a clean context, that runs the change the way someone using the shop would and only passes it if it sees that it works.

Reviewing. This is the PR phase, where CI and a code reviewer have to pass, and the reviewer can be another model, a person or both. If it's a model, it's one more reviewer: it runs the change and passes it. If it's a person, they approve it, and one never stands in for the other.

The traffic light

The four gates are always there, but you can't ask the same of a text as of the payment gateway. That's what the traffic light is for: it tells you the risk of each change, and depending on its color the gates get tougher or softer. It can be a deterministic script, a decision model or a person, and an engine gives it to you already built. Whichever it is, it looks at what was touched, not at what the agent says it did, it's recalculated at the end and it can only go up.

All we need is a script that looks at which files the change touched. What's delicate, which for now is payments/, admin/ and the migrations, is red, because what can't be undone is never green. What's harmless, like text/, is green. And we mark everything else yellow on purpose, because what nobody has classified counts as red until someone does.

Notice how many times each color calls you. An open gate is one that asks for nothing in that color:

GateGreenYellowRed
ScenarioOpenThat they're well written, and you read a few and approve themThat they're well written, and you read them all and approve them
TestingThe tests that already existAnother model creates the testsAlso tests that go through the whole shop, against the payment gateway's test environment
RefactoringLinters and typingLinters, Sonar, typing and reviewerLinters, Sonar, typing and reviewer
ReviewingCICI and another reviewerCI, another reviewer and your approval, and you check how it gets undone

Everything we've decided so far (what's delicate, which gates are needed and what each color asks for) is written in one place, the blueprint. The team approves it, and the agent can't touch it.

That table is what I would do, and each project configures it its own way: having a person review the change in red is my recommendation, not an obligation, and whether a person approves what has to pass is also up to the blueprint. A gate staying open in green isn't loosening anything either, because it was already in the blueprint. Taking a check off a gate, though, is changing the blueprint, and the team approves it.

Building it

Now we build it with what's at hand:

  • The machine checks, in CI, and CI has to pass to merge.
  • The traffic light, as one more CI step, which decides which checks are asked for.
  • The context, in the repository: the constitution in the agent's instructions file, the skills and the data schemas. What comes from outside, like the Figma design, reaches it through an MCP server or with the request.
  • What the agent can't touch, protected with the branch and a CODEOWNERS, the GitHub file that says who has to approve what: the tests, CI, the traffic-light script, the constitution and the blueprint. The approved tests also live on a separate branch, and CI compares it with the agent's. That gives you a good part of the guarantee, and only an engine gives you all of it.

The gates and the context, together, form the agent's environment, which people also call a harness. One thing is left before you trust it, and that's trying to break it: you give each check a deliberately bad case, and if it lets it through, that check isn't useful yet. The details of how to set it up in your repository are in Start today.

The journey: four changes

It's all up, so let's ask the agent for four changes, from less to more risk. In each one your job is the same: look at what happened and decide whether the blueprint worked. Before you see the result, think about what color you'd give it.

Each change goes through two moments: Brief, where we fix what has to pass, and Execute, where the agent goes through the gates. If something slips through, the last one comes, Harden.
