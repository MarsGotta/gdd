What about TDD?

If you come from TDD, GDD will sound familiar. Its cycle is red, green and refactor (you write a failing test, make it pass and clean up the code). GDD starts from the same idea, test first and code after, but it solves a different problem: whoever writes the code is an agent that can take shortcuts.

Watch the colors, because they don't mean the same thing. In TDD, red and green belong to the test, which fails or passes. In GDD they belong to the risk of the change, and a Red change is a delicate one even if all its tests pass.

AspectTDDGDD
What comes firstA failing testEverything the agent has to get past: tests, linters, reviews and approvals
Who writes whatUsually, the same person writes the test and the codeWhoever goes through the gate doesn't decide how it's validated
What prevents cheatingThe discipline of whoever programsThat the agent can't touch what judges it
What validates the testSeeing it fail for the right reasonThat, and that it catches wrong solutions
How much is demandedThe same across all the codeAccording to the risk of the change

Even the shortcut looks alike. In his book, Kent Beck proposes techniques like returning a constant, return "Hello, Ana", and generalizing it later (fake it), or writing a second case that forces you to generalize (triangulate). A person follows through to the end. An agent in a hurry can stop at the constant, and that's why the checks have more than one case and the agent can't touch them.

TDD can be part of GDD, so they don't compete. In the shop, the failing tests are your red, and the code that makes them pass, your green. The refactor is still there, with the same tests watching. And if doing TDD inside its own loop works for your agent, go ahead: GDD doesn't tell it how to work, only what it has to prove. It doesn't require it either: in a small experiment, Birgitta Böckeler saw no clear value in doing it that way, and it used 3 to more than 8 times as many tokens.
