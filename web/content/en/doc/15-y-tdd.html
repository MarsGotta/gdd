What about TDD?

If you come from TDD, GDD will sound familiar. Its cycle is red, green and refactor (you write a failing test, make it pass and clean up the code).

GDD starts from the same idea, test first and code after, but it solves a different problem: whoever writes the code is an agent that can take shortcuts.

Even the shortcut looks alike

In his book, Kent Beck proposes techniques like returning a constant, return "Hello, Ana", and generalizing it later (fake it), or writing a second case that forces you to generalize (triangulate).

A person follows through to the end. An agent in a hurry can stop at the constant, and that's why the checks have more than one case and the agent can't touch them.

TDD inside GDD

TDD can be part of GDD, so they don't compete. In the shop, the failing tests are your red, and the code that makes them pass, your green. The refactor is still there, with the same tests watching.

And if doing TDD inside its own loop works for your agent, go ahead: GDD doesn't tell it how to work, only what it has to prove.

GDD doesn't require it of you either: in a small experiment, Birgitta Böckeler saw no clear value in doing it that way, and it used 3 to more than 8 times as many tokens.

TDD is one of the ideas GDD builds on. The rest, with their sources, are in Where it comes from.

Does GDD make the agent work with TDD?

  • Yes: as in TDD, it has to write a failing test first.
  • No: GDD doesn't tell it how to work, only what it has to prove.
