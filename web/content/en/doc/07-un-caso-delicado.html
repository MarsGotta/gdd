A delicate case

In the shop you reviewed a delicate change. Now you're going inside one: it touches payment, so there's a delicate zone and, as I recommend, your approval.

Imagine you want to add discount codes to your online store. You have what almost any team has: a repository, CI and an agent. No orchestrators, no special tools.

And it's a delicate case on purpose, because it touches payment: if the method feels heavy here, everywhere else it will feel lighter.

Before you start, just once

  • You make passing CI mandatory to merge.
  • You mark payments/ and CI itself as delicate with a CODEOWNERS, and on the main branch you require review by the code owners. The file only says whose each path is: it's the branch that asks for your approval.
  • You give the agent its own credentials, with no access to production.

You set this up once. The full list, with the checks branch, is in A gate by hand.

The seven steps

  1. You decide what has to pass. You ask an agent for the rules of the codes and a few scenarios, read them and correct them.

    You also note what you expect from the change and where you will look: that the codes bring in orders, in the shop's paid orders. As for scenarios, with this one and two more, an €80 cart and an expired code, you're set:

  2. An agent writes the cases. In a separate session, it turns those scenarios into tests:

    You run them and they fail, which is what should happen. You make sure they fail because the discount is missing, not because of a broken import, and you save them on a branch the agent can't modify.

  3. Another agent gets through the gate. You open another session and hand over the job: "Make these tests pass. Don't touch them. If you think they're wrong, stop and tell me. You have two rounds of CI." And you go do something else.

  4. The gate closes. The agent says "done" and opens the PR. CI says no: the €80 test fails, because the solution it wrote is tailored to the first one.

    Nobody calls you: the error goes back to the agent and it fixes it. In the second round the tests pass, and CI confirms they're the ones you approved.

  5. You look only where it matters. Because the change touches payments/, the PR asks for your approval. You read the change, check that it can be undone and give your approval. If it had been the text on a button, you wouldn't even have known.

  6. You look at whether it helped. The change is already built and in use, but not closed yet. When you come back, a few days later, the agent shows you how many paid orders carry a code, taken from the shop and not from what it says.

    That was what you noted in the first step, and you give your verdict: yes. If you hadn't come back for a month, the change would still be there, waiting, without closing by itself.

  7. If something slips through, you harden. A week later, someone stacks two codes and the total comes out negative. That's what slipped through, and it slipped through because nobody had written it down.

    You don't rewrite the process: you add the rule, "the total never drops below €0," with its scenario and its test. If that bug comes back, the gate stops it. Hardening goes the other way too: a check that catches nothing and only costs gets relaxed or removed.

In short

And that's it. You've read a few rules and scenarios, given one approval, looked at whether it helped and added one test, without reviewing every step or installing anything. The rest is gates you add when you need them.

You mark payments/ in a CODEOWNERS. Is that enough for a change to payment to wait for your approval?

  • Yes: once it touches a marked path, the pull request can't merge without you.
  • No: your main branch also has to require review by the code owners.

That's it. The file only says whose each path is, and the branch asks for the approval when you require it. It's an approval you choose, not a rule of the method.
