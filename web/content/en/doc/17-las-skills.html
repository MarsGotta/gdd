The skills

You've set up your first gate by hand and it works. The next change you'd like to leave entirely to your agents: one writes the scenarios with you, another writes the cases, a third does the work, and someone who has seen none of that reviews it. That's a lot to explain every time, so it's written down once, in seven skills.

A skill is a file of instructions your agent loads when it needs it. The GDD ones install nothing and run nothing of their own: they use what your project already has, its tests, its linter, its CI and git. The only thing they bring that runs is a script of about twenty lines they offer you when preparing: it measures how long each check takes and, if you accept it, it becomes your project's. One is the entry skill, gdd, which hands out the work, and there are six more, one per role.

The seven

gdd-briefThe orchestrator, on every changeWhat has to pass, as scenarios, and the expected risk.
gdd-checksAnother agent, never the one that buildsThe standing checks and the cases of each change, each seen failing for the right reason.
gdd-buildThe agent that goes through the gateThe change, and the facts that prove it.
gdd-reviewThe reviewer, with a clean contextIts verdict, and the risk worked out again.
gdd-hardenThe orchestrator, with you, when something slips through or a gate stops adding anythingThe crack and the check that would have caught it, or the proposal to retire the one you don't need.

Whoever writes the cases, whoever builds the change and whoever reviews it each work in a separate agent, which starts without the others' conversation: it gets what they left written, not how they got there. That way the reviewer judges the change in front of it, without having heard how it was made (The pieces and the roles).

How to install them

You need a git repository and an agent that loads skills. On three of them, Claude Code, Codex and Antigravity, the seven come in at once, as a plugin that runs nothing of its own.

On Claude Code you type it inside the agent. It also brings three subagents, one for each role that works in an agent of its own.

On Codex it takes two steps in the terminal: you add the GDD repository as a source of plugins and install it from there.

On Antigravity you clone the repository and install the plugin from its folder.

If you'd rather keep them inside your project, copy the seven folders whose names start with gdd from the repository into .claude/skills/ on Claude Code or .agents/skills/ on Codex.

They're at version 0.9. To find out whether they're in, and to update them later on, each agent has its own commands:

The first thing you ask for

With the skills in, ask your agent to set GDD up in your project, and if you're starting from scratch, tell it in the same message what you're going to build. There's no command to remember, because gdd loads by itself. That first conversation is with you and needs your agent's deepest model: if you aren't on it, it tells you before it starts.

  1. In a new project, or if you leave the decisions to it, it reads up before it proposes anything, because tools and a sector's rules change faster than a model's memory. It looks up what a project like yours has to protect, what its sector asks for and which tools are current for what you use, and keeps a copy of each source. In what it proposes, it tells apart what comes from a source and what is its own default.
  2. It proposes the zones of your project and the gates it needs, and you correct what doesn't fit. Each gate is written as a scenario: what it asks at each level of risk and what it rejects. If your project already has history, before you approve it runs the zones over your last commits and tells you how many would have come out of each color. It asks only what changes a zone or a gate: money, accounts and permissions, personal data, what can't be undone.
  3. It looks at which agents you have installed and which models each one offers, and proposes which one does the light work, which the standard and which the deep, and which one reviews. You decide, and before it counts it checks that each one starts.
  4. It prepares the protections with you and tries them. It writes which files ask for your review, and what has to be applied on your platform you apply yourself. Then it tries four things from the environment the building agent will work in, pushing to the main branch among them. If any of them succeeds, your blueprint says so, and the agent not touching what judges it stays a rule.
  5. You approve the blueprint, or your team does if you work with one, with a commit or a pull request from a person, never from an agent. It asks you in a short message: which files to read and, before you say yes, what doesn't protect anything yet or what it couldn't confirm.
  6. Another agent sets up the standing checks, once for the whole project, and a reviewer tries to fool them and checks that the blueprint asks for what each gate says. One that some colors ask for and others don't, such as mutation testing if you keep it for red, judges only what each change adds or modifies. And if one has to reach a number, it proposes starting from the one its tool gives or your code already reaches, not from the highest. A number nobody can reach doesn't make the gate stricter, it keeps it shut. No change starts until they are on the main branch.

From there you ask for each change in your own words, and you hear about it when it needs you and when it's in. Every step, with what you say, what happens and what you end up with, is in the repository's guide.

That same repository holds the tests the skills are checked with, run with a real model.

When it needs you

While it works, it talks to you about your product and not about the method, and briefly: one line per gate, passed or failed, and the detail only when something fails, when you have to decide or when you ask for it. When it needs something from you, it asks one thing, with what it would do, so that a yes is enough.

If you tell it to decide, it decides how the work gets done and stops asking you about that. What stays yours, or your team's, is approving the blueprint and what has to pass, anything that loosens a check and what can't be undone.

So even if you've told it to decide, it won't record as debt a check that already fails without the change, or put it in quarantine, because that loosens it. Nor does it build anything while the check keeps failing, because no change would get through. It proposes one way out, something like this: "Your footer fix is written but not in yet, because a test of the cart's text already failed before I touched anything. I'd fix that first, on its own, and then both would go in. Is that all right?"

What they leave in your repository

Everything ends up in files you can read, in a gdd/ folder: the blueprint, the gates, the brief of each change with its scenarios and a log of what happened, with who approved what. Those files make sense without the skills. An engine will read and write the same ones, so what you set up today will still serve you later.

What they don't guarantee

What they don't give you is a guarantee. Without an engine, the agent not touching what judges it is a rule: the skills tell it so and then check that it hasn't, but nothing stops it. With protected branches and the permissions of your platform you get a good part of the way, and your blueprint says which of the three degrees you're at, rule, platform or engine (How a gate gets fooled). Only an engine gives the full guarantee, and what's missing without one is in The engine.

With skills or by hand, what is delicate stays delicate. What changes when the thing you touch is payment, I tell in A delicate case.
