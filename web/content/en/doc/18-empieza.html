Get started

Going from zero to your first change with GDD, in your project and with your agents, takes five steps. Reading them takes about ten minutes, and the rest depends on how long your agent takes. If you'd rather put up a gate by hand, without the skills, that's in A gate by hand.

What you need

  • A git repository, with git 2.38 or later.
  • An agent that loads skills: Claude Code 2.1.275 or later, Codex or Antigravity.
  • Rust 1.89 or later, to build the layer, a small command that comes with the skills. It gets built once in each copy of your project, and that first time it needs the network.
  • macOS or Linux. Nobody has tried it on Windows yet.

2. Check it's in

Ask for the list of plugins in a terminal, not inside the agent's session. On Claude Code, claude plugin list should show something like this, with the version you have:

❯ gdd@gdd
  Version: {{skills}}
  Scope: user
  Status: ✔ enabled

On Codex, codex plugin list shows a line gdd@gdd installed, enabled {{skills}}. On Antigravity, agy plugin list shows gdd (enabled, {{skills}}) with Components: 8 skills.

If it's on the list and your agent doesn't notice it, close the session and open another: a session that was already open doesn't load a new plugin.

3. Set GDD up in your project

Open your agent in your project's folder, on its most capable model, and type:

Set GDD up in this project

If the project is new, add in the same message what you're going to build. You don't have to name any skill: your agent loads the right one.

Your agent proposes what is delicate in your project, the zones, each with its color. Also what every change has to prove, the gates, and which model does each kind of work. It leaves that in gdd/blueprint.md, the blueprint, and in gdd/constitution.md, with what must never happen in your product and five lines about your product, starting with who it's for. The first time, it builds the layer at .gdd/gdd; if you don't have Rust, it tells you and waits.

Read it, you or your team, and tell it what to change or approve it: with a commit or a pull request of yours, or with your yes if you have no platform. It also gives you what you have to apply on your platform yourself, such as protecting the main branch and having your CI run the layer. Then your agent sets up the checks the blueprint names and tries to fool each one on purpose. No change starts until they're on the main branch.

4. Ask for your first change

In your own words:

Add a size filter to the catalog

Your agent gives the change the color of the most delicate thing it touches. If it's green, like the text on a button, it asks you nothing. If it's yellow or red, with the blueprint's template, before anyone builds it sends you the rules of the change in a short message, under 150 words, or 200 on red:

You'll only see the products that come in the size you pick.

I've assumed sizes go from small to large, not in alphabetical order.

We'll know it helped if fewer people leave the catalog without opening a product, in the shop's visit records.

You can read the scenarios in features/catalog.feature. Shall I go on with these rules?

Say yes, or correct a rule. Whatever your agent decided on its own is marked as its own, so you can see it.

5. Watch it go through the gates

When the change is in, it tells you what changed in your product and one line per gate, passed or not:

brief     yellow: it touches catalog/. Two rules, one assumed by me
cases     sealed, each one seen failing first
seal      passed
tests     failed, round 1: the jacket still shows up in M
tests     passed, round 2
lint      passed
review    passed, yellow

If a test fails, the building agent fixes it and goes through again. You do nothing. On red, with the template, you also review the change at the end, in your platform's pull request if you have one.
